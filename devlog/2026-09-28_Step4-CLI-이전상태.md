## TL;DR

1. 복습하다가 **"State에 직전 값이 있는데 왜 대화 기록을 LLM에 또 넘기지?"** 라는 의문이 생겼다. 따져 보니 Checkpointer가 들고 있는 값을 버리고, 대신 대화 기록 10개를 매번 다시 읽히고 있었다. → **대화 기록 대신 `<이전 상태>` 한 줄**을 넘기도록 바꿨다.
2. 이전 값을 **유지할지·바꿀지·더할지·비울지는 LLM이** 판단한다. "전부 보여줘"를 계좌 이름이 없다는 이유로 이전 값으로 두는 식의 규칙은 LLM을 쓰는 의미가 없다.
3. 다른 업무로 넘어갈 때는 직전에 본 계좌가 **하나면 이어받고, 둘 이상이면 되묻는다.** 처음엔 LLM에게 세게 했는데 두 개를 "하나뿐"으로 잘못 셌다 → **세는 일은 코드로** 옮겼다.
4. CLI 루프는 종료 단어로 끝내고, 실행과 표시를 나눠 Step 5 승인 받기 자리만 만들었다.
5. 이 모델은 **`temperature` 설정을 무시한다**는 걸 경고 메시지로 알게 됐다.
6. **Step 5**: 이체 처리안 → `interrupt`로 멈춰 승인 → 실행 직전 재검사 → 저장. 승인 답은 LLM 없이 정해진 단어로만, 5분 지나면 무효.
7. 테스트에서 LLM이 **코드가 적어준 "이어받을 계좌: 없음"을 무시**했다 → 알려주기로 끝내지 않고 **코드가 검증해서 막게** 했다.
8. **Step 6**: `rollback` 노드를 **뺐다** — 복사본에서 바꾸고 한 번에 교체하니 되돌릴 게 없다. 완료 기록은 거래와 같은 저장으로 남겨 둘이 어긋날 수 없게 했다.

## 2. Step 0~3 복습

Step 4 전에 지금까지 만든 것을 처음부터 다시 설명할 수 있는지 확인했다.

| 주제 | 핵심 | 내가 헷갈렸던 것 |
|---|---|---|
| 큰 그림 | LLM은 입구(`understand`)에서 번역만, 안쪽은 코드. **숫자는 LLM을 거치지 않는다** | `respond`를 틀로 만든 이유를 "토큰 절약"으로만 생각함 → 진짜 이유는 **정확성과 테스트 가능성** |
| 저장 | 무결성 검사는 **쓰기 전에**. atomic write. 실패 세 종류 | 잔액 부족을 무결성 위반으로 생각함 → 잔액 부족은 **업무상 거절**(validate), 무결성 규칙 2는 **버그를 잡는 두 번째 안전망** |
| 업무 정의 | `intents.py`는 신청서 양식, `READ_TASKS`는 업무 매뉴얼 목차 | `intents.py`가 JSON을 읽는다고 생각함 → 데이터는 `functions.py`가 읽는다 |
| LLM 입구 | 허용 목록, structured output, 추측은 밝힌다 | — |
| 그래프 | State·노드·Edge·Checkpointer. interrupt = 멈춤, checkpointer = 기억, resume = 재개 | 멈춘 자리부터 이어가는 게 interrupt 덕분이라고만 생각함 |

조회 코드가 `save`를 import하지 않는 건 **최소 권한 원칙** — "조심해서 안 바꾼다"가 아니라 "바꿀 수 없게 만든다".

## 3. Step 4 결정

### 결정 1 — LLM에 무엇을 넘길까 (복습 중 나온 의문에서 시작)

State의 `params`는 Checkpointer에 남아 있다. 그런데 `understand`는 매 턴 그걸 **통째로 새로 쓰고**, 맥락은 대화 기록 10개에서 다시 읽게 하고 있었다.

처음 설명은 "매 턴 새로 쓰지 않으면 앞 질문의 계좌 목록이 다음 질문에 남는다"였다. 하지만 그건 **코드가 규칙으로 합칠 때**의 이야기다. 합치는 판단을 LLM에 맡기면 된다.

| 안 | LLM이 보는 것 | 토큰 | 체크포인트의 이전 값 |
|---|---|---|---|
| A (기존) | 최근 메시지 10개 | 대화가 길수록 늘어남 | 안 씀 |
| **B (선택)** | 이전 상태 한 줄 + 지금 말 | 거의 일정 | **씀** |

- "생활비랑 저축" → "여행 자금도" → 셋 / "비상금은?" → 비상금 / "잔액 다시" → 비상금 유지 / "전부" → 전체
- 이체 도중 "아니 5만 원" → **금액만** 바뀌고 계좌는 유지 (기존 방식이면 계좌를 다시 물어야 했음)
- "두 번째 거"처럼 에이전트가 **보여준 목록**을 가리킬 때를 위해 보여준 후보도 이전 상태에 넣는다

**함정 하나**: 프롬프트만 고치고 Pydantic 칸 설명(`"계좌를 말하지 않았으면 빈 목록"`)은 그대로였다. 칸 설명도 LLM에게 가는 지시문이라 두 지시가 부딪힌다. "잔액 다시 알려줘"를 전체 조회로 볼 수 있어서, 칸 설명을 "이번 턴의 최종 값"으로 고치고 테스트로 박았다.

### 결정 1-2 — 업무가 바뀌면 계좌를 이어받을까

`intent`가 바뀌어도 **보고 있던 계좌까지 날아가면 안 된다** (한 계좌에서 조회·이체·카드 관리를 이어서 한다).

처음엔 "거기서"처럼 가리키는 말이 있을 때만 이어받기로 했다. 다시 생각해 보니 **생활비를 조회한 뒤 "저축으로 3만 원"이라고 하는 건 생활비에서 보내려는 것**이다. 은행 앱도 계좌 상세에서 [이체]를 누르면 그 계좌가 출금 계좌로 채워진다. 이체는 어차피 승인을 거친다.

→ 직전 계좌가 **하나**면 이어받는다. **둘 이상**(두 계좌 조회, 이체의 출금·입금)이면 어느 쪽인지 모르니 되묻는다. 이어받은 계좌는 승인 화면에서 밝힌다 (승인 피로 — 확인을 여러 번 받으면 내용을 안 읽고 "예"를 누르게 됨).

### 결정 1-3 — "주식 계좌 잔액"

`unsupported`(처리 불가)가 아니라 `uncertain`(후보 안내). 계좌에 접근하려는 요청이라 업무와 무관하지 않다. 결과가 없었을 뿐이니 **올바른 방향으로 유도**해야 한다.

### 결정 2 — 종료

정해진 단어(`종료`/`exit`/`quit`) + Ctrl+C·Ctrl+D. LLM으로 판단하면 승인 대기 중 "됐어"가 종료인지 거절인지 헷갈린다.

### 결정 3 — 방치하면?

실제로는 앱을 끄거나 그냥 떠나는 경우가 많다. 그런데 조회하다 떠나는 건 위험하지 않다 (`InMemorySaver`라 프로그램이 꺼지면 상태도 사라짐). **위험한 건 승인 화면에서 떠났다가 몇 시간 뒤 "예"를 누르는 것.** → CLI 타이머 대신 Step 5에서 **승인 유효 시간**을 둔다.

### 결정 4 — interrupt 처리 구조

재개 코드는 interrupt가 없는 지금 확인할 방법이 없다. 루프를 `run_turn`(실행) / `show_result`(표시)로 나눠 자리만 만들고 Step 5에서 채운다.

## 5. Step 5 — 즉시이체와 승인 흐름

### 흐름

```
plan_change     형식 검사(필수 칸·uncertain) → 업무 검사(validate) → 처리안 + 만든 시각
confirm_change  🛑 승인 화면 → 답 분류 (예 / 취소 / 애매 → 다시 / 5분 지남 → 무효)
apply_change    장부를 새로 읽어 같은 validate로 재검사 → 실행 → save(무결성 검사)
```

### 정한 것

| # | 무엇 | 결정 | 이유 |
|---|---|---|---|
| 1 | 이체 기록 | 두 줄을 같은 `transfer_id`로 묶고 **무결성 규칙 9** | 입금을 빠뜨린 이체를 `save()`가 막는다. 전에는 외부 출금과 구분할 수 없었다 |
| 2 | 승인 화면 | 방향·금액 + **이체 후 잔액** + 해석 안내(필요할 때만) | 금액 실수가 눈에 띈다. 안내가 매번 나오면 안 읽게 된다 |
| 3 | 애매한 답 | **정해진 단어만**, 나머지는 다시 묻기 | 돈이 나가는 마지막 관문. 모르는 답은 승인으로 치지 않는다. 계획에 있던 "애매하면 LLM"은 뺐다 |
| 4 | 유효 시간 | **5분** | OTP(3분)보다 여유, 로그아웃(10분)보다 짧게. 테스트는 시계를 앞으로 돌려서 |
| 5 | 재검사 | 같은 `validate`를 다시 | 검사 코드가 한 벌이면 어긋나지 않는다 → 검사 세 겹 |

### 확인하면서 알게 된 것

- **`interrupt`는 재개될 때 노드를 처음부터 다시 실행한다.** 그래서 `confirm_change`는 문장만 만들고, 저장은 다음 노드에 둔다.
- 재개는 `understand`를 거치지 않아서 **승인 답에는 Gemini가 불리지 않는다.**
- 멈춘 대화에 새 요청을 보내면 대기 중인 승인은 버려지고 처음부터 처리된다.
- 1차 26/27. Step 4에서 통과했던 "두 계좌를 본 뒤 여행 자금으로 3만 원"이 실패 — `<이전 상태>`에 **"이어받을 계좌: 없음"이라고 적어줬는데** LLM이 생활비를 채웠다. 같은 테스트가 한 번은 통과, 한 번은 실패. → 프롬프트는 확률이라, LLM의 답을 **코드가 검증**해서 이어받을 수 없는 계좌면 비우게 했다. 가짜 LLM(일부러 어기는 답)으로 API 없이 확인했고, 다시 돌린 실행에서도 LLM이 또 어겼지만 코드가 막았다 → **27/27**.
- 문장의 조사를 받침에 맞게 고르는 함수를 만들었다 ("저축**으로**", "생활비**로**", "즉시이체**를**").

## 6. Step 6 — 처리 기록과 실패 경로

### 정한 것

| # | 무엇 | 결정 | 이유 |
|---|---|---|---|
| 1 | `rollback` 노드 | **두지 않음** | `apply_change`는 복사본을 바꾸고 `save()`는 검사 후 한 번에 교체한다. 실패해도 파일은 그대로 — 되돌릴 게 없다. 명세의 "이체 전 상태 유지"는 동작이 아니라 결과의 요구 |
| 2 | 기록 범위 | 승인 화면까지 간 요청만. 상태에 `expired` 추가 | 즉시 거절은 그 자리에서 결과를 들었다. 만료는 취소도 실패도 아니다 |
| 3 | 기록 모양 | `intent` + `details`(ID) + `status`·`reason` + 두 시각 | 별명은 바뀔 수 있어서 ID로. `transfer_id`로 실제 거래를 찾아갈 수 있게 |
| 4 | 기록 시점 | 완료는 **거래와 같은 저장**, 나머지는 `record_result` + 무결성 규칙 10 | 따로 저장하면 "돈은 옮겨졌는데 기록이 없는" 상태가 생길 수 있다 |
| 5 | 재시도 | `data_store` 안에서 파일 쓰기만 3번 | 노드가 실패를 받아 기록하면 바깥 `RetryPolicy`는 실패를 못 본다. 원인을 아는 곳에서 |

> 처음 헷갈린 것: 처리 기록을 State에 넣는 줄 알았다. State는 **처리 중인** 접수 파일철(메모리, 끄면 사라짐)이고, 기록은 **처리 내역 대장**(장부 파일)이다.

### 확인

- 1차 31/32 (Gemini 28회). 처리 기록 순서, 저장 3번 실패 → 이체 안 됨 + 실패 기록, 마지막 무결성 10/10 모두 통과
- 실패 1개: 처리안 시각은 `...00.123456+09:00`(소수점 초), 완료 시각은 `...00+09:00` — **형식이 섞여** 같은 초에 끝나면 요청이 완료보다 늦어 보였다. 초 단위로 통일하고 가짜 LLM으로 확인
- Step 5의 "취소하면 장부 그대로" 테스트가 파일 전체를 비교하고 있었다. 이제 취소도 기록이 남으므로 **잔액·거래만** 비교하도록 고쳤다 — 테스트는 확인하려는 뜻을 정확히 표현해야 설계가 바뀌어도 버틴다

## 결정 사항 (Decision Log)

## 헷갈렸던 것 / 배운 것

- **END는 "대화 종료"가 아니라 "이번 턴 종료"**. State는 END 뒤에도 Checkpointer에 남는다. "매 턴 새로 쓴다"는 지운 게 아니라 `understand`가 **덮어쓴** 것이었다.
- **"말하지 않음"과 "전부"는 LLM 단계에서는 같은 모양(빈 목록)** 이다. B안에서는 LLM이 유지할 값을 다시 적으므로, 코드에 도착한 빈 목록은 언제나 "전체"다.
- **LLM에게 가는 지시는 프롬프트만이 아니다.** structured output을 쓰면 칸의 `description`도 지시문이다.
- **세면 알 수 있는 건 코드가.** 이번에 LLM이 두 개를 "하나뿐"으로 셌다. 흔들리면 안 되는 판단은 LLM에 두지 않는다.
- **이 모델은 `temperature`를 무시한다** (`UserWarning: ... temperature will be ignored`). "휴가비 계좌"가 어떤 실행에서는 `uncertain`, 어떤 실행에서는 "여행 자금" 추측으로 나온 이유일 수 있다. 테스트는 처음부터 둘 다 허용해 두었다 (어느 쪽이든 사용자가 속지 않음).
