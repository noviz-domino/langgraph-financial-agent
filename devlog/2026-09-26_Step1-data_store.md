## TL;DR

1. `data_store`는 **파일로 들어가는 유일한 문**이다. 저장은 반드시 `save()` 하나를 거치고, 그 안에서 무결성 검사를 해서 **틀린 장부는 파일에 들어가지 못하게** 했다.

3. 원본(`initial_data.json`)은 **개발·테스트를 위한 기준점**(seed data)이고 백업과는 다르다는 걸 정리했다. 저장은 atomic write로, 복사본은 필요할 때 자동으로 만든다.
4. Step 2에서 "사용자가 말한 계좌를 어떻게 찾을까"가 **세 번 바뀌었다.** 최종: LLM이 **역할 나누기와 이름 고르기를 한 번에** 하고(허용 목록 = 내 계좌 이름 + `uncertain`), 코드는 **검색 없이 검증만** 한다. 검증은 **형식(Pydantic) / 업무(Handler)** 두 층.
5. Step 3에서 **처음으로 그래프를 돌리고 Gemini를 불렀다.** "휴가비 계좌"(없는 이름)를 LLM이 "여행 자금"으로 추측하는 걸 발견 → 히스토리 탓인지 **실험으로 확인**(아니었음) → 막지 않고 **"'여행 자금' 계좌로 이해했어요"로 해석을 밝히기**로 해결. 8/8.

## 진행 내용

### 1. 결정 1 — 저장 전에 무결성 검사를 한다

**질문**: `save()`가 파일에 쓰기 직전에 `check_integrity()`(09-25에 만든 검사)를 부를까?

| | A. 검사 후 실패하면 거부 ✅ | B. 검사 안 함 | C. 검사하되 경고만 |
|---|---|---|---|
| 틀린 장부가 파일에 남을 수 있나 | **없음** | 있음 | 있음 |

**판단에 쓴 상황**: Step 5에서 이체 코드를 짜다가 **잔액만 바꾸고 거래 기록 추가를 깜빡한** 버그가 생겼다고 가정.

| 선택지 | 결과 |
|---|---|
| A | 저장 거부 → 파일은 원래대로 → 그래프가 `rollback`으로 → 장부 안전 |
| B | 틀린 장부가 저장됨 → 며칠 뒤 발견해도 어느 이체에서 틀어졌는지 추적 어려움 |
| C | 경고는 남지만 파일은 이미 망가짐 |

**A를 고른 결정적 이유 — 그래프의 `rollback` 경로가 진짜가 된다.**

```
apply_change → 저장 성공? ─ 성공 → record_result
                         └ 실패 → rollback → record_result
```

B·C라면 "저장 실패"는 디스크가 꽉 차는 것 같은 드문 경우에만 일어나서, `rollback`은 만들어놓고 한 번도 실행 안 되는 코드가 된다.
A라면 무결성 위반이 저장 실패의 원인이 되어, **틀린 데이터를 일부러 저장해보는 것만으로 `rollback`을 테스트**할 수 있다.

> 실무 데이터베이스의 **제약 조건**(constraint)과 같은 원리다. 규칙을 어기는 저장을 DB가 거부한다.
> 원칙은 **"저장하는 곳에서 막는다."** 저장 통로가 하나라서 관문도 하나만 세우면 된다.

**A의 단점**: 저장할 때마다 거래 전체를 훑는다. 거래 30건이라 문제없고, 수백만 건이라면 애초에 JSON이 아니라 DB를 쓴다.

### 2. 실패는 세 종류다 → 기획서 설계 원칙 6

에러 처리를 만들기 전에 **무엇이 에러이고 무엇이 아닌지**부터 정했다.

| 종류 | 예 | 다루는 법 |
|---|---|---|
| **업무상 거절** | 잔액 부족, 없는 계좌 | **에러가 아니다.** 평범한 결과로 돌려준다 |
| **저장 실패** | 무결성 위반, 파일 잠김, 깨진 JSON | **우리 에러를 낸다** → 받는 쪽이 `rollback` |
| **버그** | 오타로 인한 `KeyError` | **받지 않는다.** 터지게 둬서 빨리 발견 |

- 잔액 부족은 은행에서 매일 일어나는 일이다. 에러(예외)는 **예상하지 못한 일**에 쓰는 도구라, 평범한 거절까지 에러로 만들면 진짜 사고와 섞인다
- 반대로 모든 에러를 받아버리면 오타 하나도 "저장에 실패했습니다"로 뭉개져 원인을 못 찾는다

**저장 실패용 에러 — "다시 하면 되느냐"로 나눴다**

```
DataStoreError        ← 둘을 한꺼번에 받을 때 (apply_change)
├── IntegrityError    ← 데이터가 틀림. 같은 데이터라 다시 해도 실패
└── StorageError      ← 파일 문제. 편집기를 닫으면 성공할 수 있음
```

나눈 이유는 27번 노트의 `RetryPolicy`와 `retry_on`(재시도할 예외 종류만 선별) 때문이다. 나중에 재시도를 붙일 때 **파일 문제만 골라서** 재시도할 수 있다.

부모-자식 구조로 만들면 받는 쪽이 **필요한 만큼만 자세하게** 받을 수 있다. 파이썬의 `FileNotFoundError`와 `PermissionError`가 둘 다 `OSError`의 자식인 것과 같은 구조.

`IntegrityError`라는 이름은 파이썬 DB 라이브러리(`sqlite3` 등)가 제약 조건 위반 때 내는 에러 이름과 같게 지었다.

> **Windows 함정**: `bank_data.json`을 메모장·VSCode로 열어둔 채 저장하면 파일 교체가 `PermissionError`로 거부된다.
> 테스트하면서 파일을 열어보다가 겪을 가능성이 높다. `StorageError`로 나타나고, 편집기를 닫으면 해결된다.

### 3. 작업용 복사본 — 개념 정리

**원본과 복사본으로 나누는 건 과제 명세의 요구사항**이다.

| 파일 | 비유 | 프로그램이 고치나 |
|---|---|---|
| `initial_data.json` | 게임의 "새 게임" / 시험지 원본 | ❌ |
| `bank_data.json` | 세이브 파일 / 풀고 있는 복사본 | ✅ |

파일이 하나뿐이면 테스트할수록 데이터가 바뀌어서 처음 상태로 돌아갈 방법이 없다. 둘로 나누면 원본을 다시 복사해서 언제든 **맨 처음**으로 돌아갈 수 있다(`reset()`).

**처음 오해: "서버 데이터 백업처럼, 시간을 두고 갱신해서 롤백하는 건가?"** → 다르다.

| | 서버 백업 | 원본/복사본 (seed data) |
|---|---|---|
| 보관본이 갱신되나 | ✅ 주기적으로 현재 상태를 새로 떠둠 | ❌ 처음 상태 그대로 |
| 되돌리면 | 최근 백업 시점으로 | **맨 처음**으로 |
| 목적 | 사고 때 최근 데이터 살리기 | 테스트를 **같은 조건에서** 반복하기 |

"롤백"이라는 말이 붙는 개념이 세 개라 구분해뒀다.

| 개념 | 무엇을 되돌리나 | 누가 |
|---|---|---|
| `reset()` (원본 다시 복사) | 모든 변경 → 맨 처음 | 사람이 테스트용으로 |
| 그래프의 `rollback` 노드 | **방금 실패한 저장 한 번** | 프로그램이 자동으로 |
| 백업 복구 | 마지막 백업 이후 전부 | 운영자 (**이 프로젝트엔 없음**) |

그래프의 `rollback`은 원본을 쓰지 않는다. 검사에서 막히거나 atomic write로 교체에 실패하면 `bank_data.json`은 **저장 직전 상태 그대로** 남아 있기 때문에, `rollback`은 되돌린다기보다 "안 바뀌었음을 확인하고 사유를 남기는" 역할이다.

> 22번 Time Travel이 "시점별로 되돌리기"에 가깝지만, 그건 **대화 상태**(Checkpointer)에 대한 것이고 은행 데이터에는 적용되지 않는다. 09-22에 정리한 "저장소가 두 개"와 같은 구분.

**두 번째 질문: "0원부터 시작한다고 했는데, 원본은 안 바뀐 건가?"** → 어제 **바뀌었다.** 다만 누가 바꿨느냐가 다르다.

| 누가 | 원본을 바꿔도 되나 |
|---|---|
| 프로그램 (실행 중) | ❌ 절대 안 됨 |
| 개발자 (설계를 고칠 때) | ✅ 됨. 대신 git으로 기록 (`9137f96 fix: 초기 거래 내역을...`) |

그리고 "0원 시작"은 **잔액이 0원이라는 뜻이 아니다.** 잔액은 그대로(생활비 520,000원)이고, "계좌 개설 순간엔 0원이었다고 보고 거래를 쌓으면 지금 잔액이 나와야 한다"는 **검사 규칙**이다. 바뀐 건 거래 내역(20건 → 30건)뿐.

> 복사본이 이미 있는 상태에서 원본을 고치면, 복사본엔 반영이 안 된다 → `reset()` 필요.
> 실무에서 seed data를 바꾼 커밋에 "reset 필요"라고 적어두는 관례가 있다. 앞으로 원본을 고칠 땐 그렇게 적는다.

**결론: 원본은 개발·테스트를 위해 항상 같은 조건에서 시작하는 기준점이다.**

### 4. 결정 2 — 복사본은 필요할 때 자동으로 만든다

| | A. `load()`가 필요할 때 자동으로 ✅ | B. `main.py` 시작할 때 | C. 사람이 직접 |
|---|---|---|---|
| 단점 | 언제 복사됐는지 덜 보임 → **로그로 보완** | `main.py`를 안 거치는 곳에서 실패 | 깜빡하면 실패 |

`load()`를 부르는 곳이 `main.py`만이 아니다 — 조회 함수 확인(Step 2), 그래프 확인(Step 3), 나중의 테스트. 확인 책임을 여러 호출자에게 나눠주지 않고 `load()` 한 곳에 둔다.

이 방식을 **lazy initialization**(지연 초기화 — 미리 준비하지 않고 처음 필요해지는 순간에 준비)이라 부른다. 복사할 때 로그를 남겨서 29번 `logging`을 처음 썼다.

### 5. 결정 3 — atomic write

atomic = "더 쪼갤 수 없는". 저장이 **완전히 되거나, 아예 안 되거나** 둘 중 하나만 일어나는 방식.

**그냥 쓰면 생기는 문제**: 파일을 쓰기 모드로 여는 순간 기존 내용이 먼저 지워진다. 쓰는 도중 죽으면 **반쯤 쓰인 JSON**이 남고, 원래 데이터도 이미 지워져서 되살릴 수 없다.

**atomic write의 순서** (1번 결정의 검사까지 포함)

```
save(data)
  [0] 무결성 검사 ── 실패 → IntegrityError  (파일 하나도 안 건드림)
  [1] 임시 파일(bank_data.json.tmp)에 끝까지 쓰기 + 디스크에 확실히 기록
  [2] 임시 파일로 진짜 파일을 한 번에 교체 ── 실패 → StorageError (진짜 파일은 옛날 그대로)
```

[2]의 "한 번에 교체"는 **운영체제가 보장**한다 — 옛 파일 아니면 새 파일, 반쪽은 없다. 편집기와 git도 파일을 저장할 때 같은 방식을 쓴다.

| 세부 결정 | 선택 | 이유 |
|---|---|---|
| 임시 파일 위치 | 진짜 파일과 **같은 `data/` 폴더** | 교체가 한 번에 되려면 같은 드라이브여야 함 |
| 임시 파일 이름 | 고정 `bank_data.json.tmp` | 무작위 이름은 찌꺼기가 쌓임. 동시 접속은 비목표 |
| 디스크 기록 확인 | `fsync` 포함 | 운영체제가 "나중에 쓰자"며 메모리에만 두는 경우 대비 (정전 시 빈 파일 방지) |
| 실패 시 | `.tmp` 정리 후 `StorageError` | 찌꺼기를 남기지 않음 |

`fsync` = file synchronize. 메모리와 디스크의 내용을 **지금 맞춰라**는 명령. 우리 과제에선 정전이 드물지만, 두 줄이면 되고 atomic write의 교과서적인 완성형이라 넣었다.

> 쓰는 쪽을 안전하게 만들면 읽는 쪽이 공짜로 안전해진다. `load()`가 읽는 파일은 항상 완전한 파일(옛것이든 새것이든)이다.

|---|---|
| `encoding="utf-8"` | **Windows 함정.** 안 적으면 한국어 Windows 기본값 `cp949`로 저장됨 → Mac에서 읽으면 깨짐, 일부 문자는 저장부터 실패 |
| `ensure_ascii=False` | 안 하면 한글이 `"생활비"`처럼 저장돼 사람이 못 읽음 |
| `indent=2` | 안 하면 전체가 한 줄 |
| 파일 끝 줄바꿈 | 일부 도구의 "파일 끝에 줄바꿈 없음" 경고 방지 |

**`indent=2`의 뜻**: indent = 들여쓰다. 숫자는 **한 층 안으로 들어갈 때마다 띄울 공백 칸 수.** 내용은 같고 사람이 볼 때만 달라진다.
2인 이유는 **JSON은 2칸이 업계 관례**(`package.json`, VSCode 설정, Prettier 기본값)라서. 파이썬 코드는 PEP 8에 따라 4칸이 관례라, "코드는 4칸 / 코드가 저장하는 JSON은 2칸"이 자연스러운 조합이다.

> 원본은 한 항목을 한 줄로 손으로 맞췄고, 복사본은 `indent=2`라 필드마다 한 줄씩 나온다. **내용은 같고 모양만 다르다.** 복사본은 git에 안 올라가서 문제없다.

**2·3번을 합치면**: 복사를 "파일 통째로 복사"가 아니라 **"원본을 읽어서 `save()`로 저장"** 으로 했다. 그러면 복사도 무결성 검사와 atomic write를 똑같이 거친다. 원본이 규칙을 어기고 있으면 복사하는 순간 알 수 있다.

### 7. 완성된 모양 — 개념 한 장

```
        다른 모든 코드 (그래프 노드, 조회 함수, 테스트)
                     │
          load()  ───┼───  save()        ← 파일로 가는 유일한 문
                     │
     ┌───────────────┴────────────────┐
     │  data_store                     │
     │  읽을 때: 복사본이 없으면 만든다    │
     │  쓸 때:  검사 → 임시 파일 → 교체   │
     └───────────────┬────────────────┘
                     │
      initial_data.json      bank_data.json
      (원본, 읽기만)           (복사본, 여기만 고침)
```

그래프에서 쓰이는 곳:

```
read_task    → load()만 쓴다 (읽기 전용)
apply_change → load() → 데이터 수정 → save()
                                       ├─ 성공 → record_result
                                       └─ 실패(DataStoreError) → rollback
```

> 네 결정이 전부 **"책임을 한 곳에 모은다"** 에서 나왔다. 저장 문 하나, 그 안의 검사 하나, 복사본 확인 하나, 복사도 같은 문.
> 이 파일이 튼튼하면 Step 5에서 이체 코드를 짤 때 "저장이 잘못되면?"을 걱정하지 않고 업무 로직에만 집중할 수 있다.

> 실무라면 이 확인을 `tests/` 폴더의 별도 테스트로 빼고, 진짜 `data/` 대신 임시 폴더를 쓴다.

### 9. Step 2 — "사용자가 말한 계좌를 어떻게 찾을까" (세 번 바뀐 과정)

이 결정은 **내가 반론을 낼 때마다 설계가 더 단순해진** 경우라, 과정 자체를 남긴다.

#### 1안 — LLM은 옮겨 적고, 코드가 글자로 검색 (처음 안)

```
"여행 계좌 잔액"  →  LLM: accounts = "여행 계좌" (말한 그대로)
                  →  코드: 공백·"계좌"·"통장" 떼기 → 정확히 같은 것 → 없으면 포함된 것 → "여행 자금"
```

전제는 "LLM은 우리 계좌 목록을 모른다"였다.

**내 반론 1**: 15번 Router 실습에서 LLM이 입력을 **정해진 목록 중 하나로 분류**하는 걸 이미 했다. 왜 안 된다는 건가?

```python
# 15-router.ipynb — 허용값을 Literal로 제한하고 "모르겠음"(uncertain)을 넣는다
Route = Literal["refund", "shipping", "general", "uncertain"]
classifier = llm_lite.with_structured_output(Classification)
```

→ 맞다. "LLM이 모른다"는 건 **목록을 안 주기로 정했기 때문**이었지 원래 안 되는 게 아니었다.
그리고 "여행 갈 때 쓰는 통장"처럼 **뜻으로 말한 표현**은 글자 검색으로는 절대 못 찾고 LLM만 찾을 수 있다.

**차이 하나**: 15번은 목록이 **코드에 고정**(`refund`, `shipping`)이고, 계좌는 **데이터에서 온다**(사람마다 다르고 별명이 바뀜). 그래서 실행할 때 `data_store.load()`로 내 계좌 이름을 읽어 목록을 만든다. **이름만** 넘기고 잔액은 넘기지 않는다(필요 없는 데이터를 외부 API에 보내지 않기).

#### 2안 — 규칙 먼저, 정확히 겹치면 "맞나요?" 확인, 아니면 LLM (내 제안)

**조정한 부분**:

| 내 제안 | 조정 | 이유 |
|---|---|---|
| 정확히 겹치면 "생활비 맞나요?" | **묻지 않고 진행** | 가장 확실한 경우에 묻는 것. 조회는 결과로 드러나고, 변경은 `confirm_change`가 어차피 묻는다. 같은 질문을 두 번 하면 **확인 피로** — 사람들이 읽지 않고 "응"만 누르게 됨 |
| 자원 절약 | 실제로는 **거의 비김** | `understand`가 intent 때문에 어차피 매번 LLM을 1회 부른다. 규칙 먼저 방식은 평소엔 계좌 이름 몇 개(수십 토큰)를 아끼지만, 규칙으로 못 찾을 땐 호출이 **2회**로 늘어남 |

> 자원을 아낄 때는 **무엇이 실제로 비싼지 먼저 잰다.** 여기서 비싼 건 토큰 몇 개가 아니라
> **API 호출 횟수(기다리는 시간)** 와 **사용자가 대답해야 하는 횟수**. 사용자의 대답 한 번은 API 호출보다 비싼 자원이다.
> LLM 호출을 정말 줄이려면 손댈 곳은 `understand`의 intent 판단 자체다 (나중의 최적화 과제).

"fake LLM"이라는 말도 정리했다. LangChain의 fake LLM(`FakeListChatModel` 등)은 **테스트용 가짜 모델**(미리 정한 답만 돌려줌)이다. 내가 말한 건 **규칙 기반 처리**(15번의 Deterministic Routing)였다.

**내 반론 2 — 내가 확인을 넣으려던 진짜 이유**: 한 문장에 계좌 이름이 **두 개 이상** 나오면 규칙으로는 어느 게 무슨 역할인지 판단할 수 없다.

→ 맞는 걱정이다. 문장 전체에 규칙을 적용하면 안 된다. **역할 나누기("~에서" = 출금, "~으로" = 입금)는 LLM이** 해서 slot별로 나눠 담고, 이름 찾기는 칸 하나씩 한다.
그리고 이 걱정 덕분에 **빈 곳을 찾았다** — 조회 slot이 `account` 하나뿐이라 "생활비랑 저축 잔액 보여줘"를 담을 자리가 없었다. → **`accounts` 목록**으로 변경.

> 0개·1개·여러 개를 **경계 조건**(edge case)이라 부르고 버그가 가장 많이 숨는 곳이다.
> 설계할 때 "이 칸에 값이 두 개 들어오면? 하나도 안 들어오면?"을 꼭 묻는다.

#### 3안 (최종) — LLM이 나누고 고르고, 코드는 검증만

**내 반론 3**: LLM이 이미 역할별로 나눠 담았고, 허용값으로 답을 강제한다면 규칙(검색)이 왜 필요한가?

→ 필요 없다. 검색이 필요했던 건 "LLM이 말한 그대로 적는다"는 전제 때문이었다. 허용값을 강제하면 State에 들어오는 값이 **이미 실제 계좌 이름**이다.

```
허용값: [생활비, 저축, 여행 자금, 비상금, uncertain]

"생활비에서 여행 갈 때 쓰는 통장으로 10만원"
    ↓ understand (LLM 1회) — 역할 나누기 + 이름 고르기를 한 번에
from_account = "생활비",  to_account = "여행 자금",  amount = 100000
```

| | 2안 (규칙 먼저) | 3안 (최종) |
|---|---|---|
| LLM 호출 | 1회, 못 찾으면 2회 | **항상 1회** |
| 뜻으로 말한 표현 | 규칙 실패 → 추가 호출 | 처음부터 해결 |
| 만들 코드 | 규칙 검색 + LLM 분류 + 검증 | **검증만** |

slot 값은 세 가지 상태를 구분한다.

| 값 | 뜻 | 행동 |
|---|---|---|
| 실제 이름 | 확실히 그 대상 | 진행 |
| `uncertain` | 말은 했는데 어느 것인지 모름 | 후보를 보여주며 되묻기 |
| 비어 있음 | 아예 말하지 않음 | 필수면 되묻기 |

`reason`(판단 근거) 칸도 받는다. 15번 노트대로 "`reason`은 관찰·디버깅용, 분기는 제한된 값으로".

2안에서 제안했던 "LLM이 뽑은 표현이 원래 문장에 있는지 대조"는 **뺐다.** "여행 자금"은 원래 문장에 없는 글자이기 때문. 설계가 바뀌면 딸린 안전장치도 다시 본다.

#### 검증은 두 층 — Pydantic으로 되는 것과 안 되는 것

**내 질문**: Pydantic에 상속해서 구조를 검증하고 오류를 내는 게 있지 않았나? 규칙을 따로 만들어야 하나?

→ 형식은 **Pydantic 모델에 선언만** 하면 된다. 28번 실습이 정확히 이 구조였다.

```python
# 28-agent-tool-control.ipynb
class TransferArgs(BaseModel):
    amount: int = Field(gt=0, le=1000000)       # 1층 형식: 정수, 100만 이하
MAX_TRANSFER = 100000                            # 2층 업무: 실제 한도 10만 원 (코드에서 따로 검사)
```

| 층 | 무엇을 보나 | 누가 | 어기면 |
|---|---|---|---|
| 형식 | "LLM이 약속을 지켰나" (허용 목록 안인가, 정수인가) | **Pydantic 선언** | `ValidationError` = LLM의 실수 |
| 업무 | "사용자 요청이 실행할 수 있나" (금액 > 0, 출금 ≠ 입금, 잔액) | **Handler `validate`** | 업무상 거절 = 사유 안내 |

**"금액 > 0"을 Pydantic에 넣지 않은 이유**: 명세에 "-1만 원 옮겨줘" → 이유를 안내하라는 예시가 있다. 사용자가 정말 -1만 원이라고 말했으면 LLM은 **실수하지 않은 것**이다. Pydantic이 막으면 LLM의 형식 실패처럼 보여서 "이체 금액은 0원보다 커야 합니다"라고 말할 수 없다. "출금 ≠ 입금"도 같은 이유.

> 판단 기준: **"LLM이 지켜야 하는 약속"은 Pydantic, "사용자 요청이 말이 되는가"는 코드.**
> 누구의 실수인지에 따라 층을 나누는 것 — 설계 원칙 6(실패 세 종류)과 같은 생각이다.
> Pydantic에는 여러 칸을 함께 보는 `@model_validator`도 있지만, **넣을 수 있다고 넣어야 하는 건 아니다.**

#### 따라 들어간 것 — 무결성 규칙 8

이름 → ID 바꾸기가 검색이 아니라 **표에서 찾아보기**가 되려면 한 사람 안에서 이름이 1:1이어야 한다.
→ `integrity.py` 규칙 8: **같은 소유자의 계좌 별명·카드 이름은 겹치지 않음** (다른 소유자끼리는 허용). 카드도 Step 7에서 같은 방식으로 고르므로 함께 넣었다.

빨간불 먼저 확인:

```
실제 데이터 규칙8 위반: 0                                   ← user_01·user_02의 "생활비"는 소유자가 달라 정상
저축 중복 규칙8 위반: ["user_01의 accounts에 '저축' 중복"]    ← 비상금을 "저축"으로 바꿔본 데이터
결과: 8/8 통과 (initial_data.json)
```

#### 세 사람의 역할 분담 — 이 결정의 핵심

| 누가 | 잘하는 일 | 여기서 맡은 것 |
|---|---|---|
| **LLM** | 문장 구조·뜻 이해 | 역할 나누기, 허용 목록에서 이름 고르기 |
| **코드** | 정해진 규칙을 항상 똑같이 | 형식은 Pydantic, 업무 검사, 이름 → ID |
| **사람** | 되돌릴 수 없는 일 전의 최종 판단 | `confirm_change`에서 실제 이름·방향 확인 |

### 10. Step 2 구현 — 조회 결과의 모양

계좌 찾기 방식이 바뀌면서 남은 결정은 **결과의 모양** 두 가지였다.

**㉠ 무엇을 넣나 → ID·이름·잔액**

| 칸 | 왜 |
|---|---|
| `account_id` | 사용자에게는 **안 보여준다.** "그 계좌에서 10만 원 보내줘" 같은 후속 대화에서 방금 보여준 계좌를 바로 이어 쓰기 위한 것 (명세의 "대화 대상 확인") |
| `nickname`, `balance` | 사용자에게 보여줄 것 |
| ~~`owner_id`~~ | 내부 정보라 뺀다 |

잔액은 **숫자 그대로**(`520000`) 돌려준다. "520,000원"처럼 꾸미는 건 `respond`의 일이다.
**함수는 데이터를, `respond`는 문장을** 맡는다. 나중에 음성 응답이나 영어 응답을 붙여도 조회 함수는 그대로 두고 `respond`만 바꾸면 된다.

**㉡ 내 계좌에 없는 이름이 들어오면 → `ValueError`로 드러낸다**

3안에서는 이름이 허용 목록에서 골라져 오므로 **정상이라면 일어나지 않는다.** 들어왔다면 앞 단계가 약속을 어긴 **버그**다. 조용히 빼면 계좌 일부가 말없이 사라진 결과가 나가고 버그가 숨는다.

> 3안을 고른 덕분에 생긴 이점이다. 1안(글자 검색)이었다면 "못 찾음"은 사용자가 이름을 잘못 말한
> 평범한 상황이라 안내 문장이 필요했다. 3안에서는 그 경우를 LLM이 `uncertain`으로 앞에서 처리하므로,
> 조회 함수까지 온 "없는 이름"은 순수하게 버그가 된다. **앞 단계가 책임을 가져가면 뒤 단계는 단순해진다.**

**구현에서 지킨 것**

- 소유자 필터(인가)는 `_my_accounts()` 한 곳에서. user_02의 계좌는 여기서 걸러진다
- 결과는 **필요한 칸만 새로 만든 dict**로 돌려준다 → 내부 정보가 빠지고, 받는 쪽이 결과를 고쳐도 원래 데이터는 안 바뀐다
- `functions.py`는 `save`를 import하지 않는다 → 조회가 데이터를 바꿀 방법 자체가 없다

**실행 확인** (`uv run python src/functions.py`) — API 호출 없음

| 확인 | 결과 |
|---|---|
| 지정하지 않으면 내 계좌 4개 / user_02 계좌 없음 / 빈 목록도 전체 | OK |
| `["생활비"]` → 1개(acc_001) / `["생활비", "저축"]` → 2개 | OK |
| 돌려주는 칸은 `account_id`·`nickname`·`balance`뿐 / 잔액은 정수 | OK |
| 내 계좌에 없는 이름(`"휴가비"`) → `ValueError` | OK |
| 받은 결과를 고쳐도 원래 데이터는 그대로 | OK |

```
결과: 9/9 통과
결과: 8/8 통과 (bank_data.json)      ← 조회 뒤에도 장부 그대로
```

### 11. Step 3 준비 — API 키 설정

**요청**: 실습 때 쓰던 공용 키 파일(실습 폴더의 `.env`)을 절대경로로 지정해서 쓰되, GitHub에는 절대 올라가면 안 된다.

**코드에 절대경로를 적지 않았다**

| 코드에 적으면 | 문제 |
|---|---|
| `load_dotenv("<내 컴퓨터의 절대경로>/.env")` | 코드는 커밋 대상 → 내 사용자 이름과 폴더 구조가 공개됨. 채점자 컴퓨터에는 그 경로가 없어서 동작하지 않음 |

**두 단계로 나눴다**

```
프로젝트 .env (git 제외)                  공용 키 파일 (프로젝트 밖)
  SHARED_ENV_FILE=<절대경로>  ──────────▶  GEMINI_API_KEY=...
  LANGSMITH_PROJECT=langgraph-financial-agent
```

- 코드(`src/config.py`)에는 경로도 키도 없다
- 절대경로는 git에 안 올라가는 프로젝트 `.env`에만
- 채점자는 프로젝트 `.env`에 키를 직접 넣으면 된다 (`.env.example`에 두 방법 모두 안내)

**읽는 순서가 곧 우선순위**: `load_dotenv`는 이미 있는 값을 덮어쓰지 않아서 **먼저 읽은 값이 이긴다.** 프로젝트 `.env`를 먼저 읽으므로, 공용 파일의 실습용 `LANGSMITH_PROJECT` 대신 이 프로젝트 이름이 쓰인다 (실행 기록이 실습 기록과 섞이지 않게).

**키 이름 차이**: 공용 파일은 `GEMINI_API_KEY`, 처음 만든 견본은 `GOOGLE_API_KEY`였다 → 둘 다 받도록 했다.

**fail fast**: 키가 없으면 LLM을 부르는 순간 알 수 없는 에러가 나는 대신, 프로그램을 시작할 때 `ConfigError`로 "키가 없습니다. 이렇게 하세요"를 알린다.

**키 값은 한 번도 출력하지 않았다.** 공용 파일은 존재 여부와 **변수 이름만** 확인했고, 확인 코드도 True/False만 보여준다.

```
읽은 파일: 프로젝트 .env, 공용 키 파일
GEMINI_API_KEY 설정됨: True
GOOGLE_API_KEY 설정됨: False
LANGSMITH_PROJECT: langgraph-financial-agent      ← 프로젝트 값이 이김
```

커밋 전 검사에 **내 컴퓨터의 절대경로 패턴**(사용자 폴더 경로, 공용 키 파일이 있는 폴더 이름)을 추가했다. 키만큼은 아니어도 개인 컴퓨터 정보라서.
실제로 이 일지를 처음 쓸 때 설명하느라 폴더 이름을 그대로 적었다가, 커밋 전 검사에서 걸려서 고쳤다. **문서도 커밋 대상**이라는 걸 잊기 쉽다.

### 12. Step 3 — 조회 경로 그래프 (처음으로 LLM 호출)

```
START → understand → route_request → read_task → respond → END
```

#### 결정 1 — State 칸

09-22에 설계한 9개 칸 중 **지금 쓰는 4개만** 만들었다 (walking skeleton). 칸 추가는 한 줄이라 필요할 때 붙인다.

| 칸 | 수명 | 누가 쓰고 누가 읽나 |
|---|---|---|
| `messages` | **대화 내내** 쌓임 (`add_messages`) | 입력·`respond`가 쓰고 `understand`가 읽음 |
| `intent`, `params` | **한 턴** | `understand`가 쓰고 `route_request`·`read_task`가 읽음 |
| `result` | **한 턴** | `read_task`가 쓰고 `respond`가 읽음 |

- `messages`는 그냥 이어 붙이는 `add` 대신 LangGraph의 **`add_messages`** (같은 메시지는 중복으로 쌓지 않고 교체)
- LLM의 판단 근거(`reason`)는 **State가 아니라 로그**로. 기준: **"State에는 다른 노드가 읽는 것만 넣는다"**
- Checkpointer가 대화 내내 State를 들고 있으므로, **한 턴짜리 칸은 `understand`가 매번 통째로 새로 쓴다.** 안 그러면 "생활비랑 저축" 다음 "전부 보여줘"에서 앞의 계좌 목록이 남는다

#### 결정 2 — `understand` 구성

| | 결정 |
|---|---|
| 받는 모양 | intent와 **모든 slot**을 한 번의 호출로. 고른 intent와 상관없는 칸은 코드가 버림 (`intents.py` 기준) |
| 허용 목록 | intent는 `intents.py`(코드), 계좌·카드 이름은 데이터에서 **실행할 때마다** → `create_model`로 모델을 그 자리에서 만듦. **이름만** 넘기고 잔액은 안 넘김 |
| intent 선택지 | `unsupported` 추가 — 없으면 LLM이 "날씨"를 물어도 계좌 조회를 억지로 고름 |
| LLM 실패 | "요청을 이해하지 못했어요" (재시도는 Step 6) |

**질문: "이게 답변을 구조화하는 거지?"** → 맞다. 04번의 Structured Output 그대로다. 다만 구조화하는 건 **사용자에게 보여줄 답이 아니라 LLM이 코드에게 넘기는 답**이다.

| | `understand`의 LLM 답 | `respond`의 최종 답변 |
|---|---|---|
| 누구에게 | 코드 | 사용자 |
| 모양 | 정해진 칸 | 사람이 읽는 문장 |

지시문은 두 곳에 나눠 들어간다 — 시스템 프롬프트(역할·전체 규칙)와 **각 칸의 `description`**(그 칸에 무엇을 넣을지. `with_structured_output`이 그대로 LLM에 전달). 가장 중요한 규칙은 **"말하지 않은 칸은 비워둔다"** — LLM은 빈칸을 그럴듯하게 채우려는 경향이 있어서, 출금 계좌를 멋대로 채우면 되물을 기회가 사라진다.

**질문: "Zev"를 쓰면 더 가벼워질까?** → 찾아보니 이름은 **Jev**(TypeSafe AI, 2026-09-15 얼리 액세스). 문장을 만들지 않고 **선택지 중 고른 값과 확률만** 돌려주는 모델이다.

| 칸 | Jev로 되나 |
|---|---|
| `intent`, 계좌·카드 이름 | 선택지라 맞음 (실행 중 만드는 목록 지원은 확인 필요) |
| `amount` ("10만 원" → 100000) | **안 됨** — 자유로운 숫자 추출 불가, 계산이 약점 |
| 최종 답변 문장 | 안 됨 |

금액 때문에 Gemini를 또 불러야 해서 오히려 호출이 2회가 된다 → 1차는 Gemini 그대로. 다만 **확률을 준다는 점**이 15번 노트의 "LLM이 만든 확률값은 믿지 말라"를 보완할 수 있어서, 기획서 향후 확장에 **승인 응답 분류·애매함 판단 시험 후보**로 적었다.

#### 결정 3 — `respond`는 정해진 틀로

| | A. 정해진 틀 ✅ | B. LLM |
|---|---|---|
| 호출 (질문당) | **1회** | 2회 |
| 숫자가 틀릴 위험 | 없음 | 있음 (자릿수, 직접 계산한 합계) |
| 같은 질문에 같은 답 | 항상 | 매번 다름 |

B로 하면 "모두 합치면 2,755,000원입니다"처럼 **묻지 않은 걸 덧붙이기도** 한다 (잔액 합산은 2차 기능). 은행 앱에서 숫자는 틀리면 안 된다.
틀은 `functions.py`에 업무 함수와 나란히 두고(`READ_TASKS` 표), `respond`는 찾아 쓰기만 → 업무가 늘어도 그래프는 그대로.
**음성 모드가 들어오면** B(정확히는 "숫자는 틀, 말투만 LLM")를 다시 검토한다. 그때 A가 안전망이 된다.

#### 구현의 핵심 개념

- **LLM은 입구 한 곳에만** — Gemini를 부르는 건 `understand`뿐. 나머지는 코드
- **그래프는 표만 본다** — `read_task`·`respond`는 업무 이름을 모르고 `READ_TASKS`에서 찾음. 그래프를 만들 때 `READ_TASKS`와 `READ_INTENTS`가 맞는지 먼저 확인
- **LLM 호출 한 줄만 `try`로** — 넓게 감싸면 우리 코드의 버그까지 "이해하지 못했어요"로 뭉개짐. API 키 확인은 일부러 `try` 밖 (설정 문제는 바로 멈춰야 함)

#### 첫 실행 — 6/7, "휴가비 계좌"에서 실패

```
[FAIL] 휴가비 계좌 잔액 알려줘 -> 여행 자금 계좌 잔액은 310,000원입니다.
```

없는 이름이라 `uncertain`이 나와야 했는데 LLM이 "여행 자금"을 골랐다. 15번에서 본 현상(애매해도 하나를 골라버림)과 같다.

**내 가설**: 앞에서 "여행 갈 때 쓰는 통장 → 여행 자금"을 물었으니, 히스토리에 남아서 끌려간 것 아닌가? 메모리가 켜져 있나?

→ 메모리는 **켜져 있다.** 확인 코드가 질문 6개를 **한 대화(`thread_id`)** 로 물었고, Checkpointer가 기록을 들고 있고, `understand`가 최근 10개 메시지를 LLM에 같이 넘긴다. 가설이 충분히 말이 된다.

**통제 실험** — 히스토리만 없애고 나머지는 그대로: 새 대화에서 "휴가비 계좌 잔액 알려줘" 하나만.

```
understand: intent=account_list_with_balance params={'accounts': ['여행 자금']}
            reason=사용자가 휴가비 계좌의 잔액 조회를 요청했으므로 여행 자금 계좌 조회를 선택했습니다.
```

→ 히스토리가 없어도 같은 결과. **원인은 히스토리가 아니라 뜻으로 추측하는 경향.** 그리고 `reason`을 보면 LLM은 **추측했다는 표시를 전혀 하지 않는다.**

> 가설이 틀렸다고 헛수고는 아니다. **히스토리가 해석을 끌고 갈 위험 자체는 실제로 있다.** "그 계좌에서 보내줘" 같은 후속 대화(명세의 "대화 대상 확인")를 만들 때 다시 신경 써야 할 부분이다.
> 그리고 이 실험으로 **확인 코드의 약점**이 드러났다 — "이어 묻기"를 보려고 모든 질문을 한 대화로 물었더니, 각 질문이 앞 질문의 영향을 받을 수 있게 됐다. 한 테스트가 두 가지를 동시에 확인하려다 섞인 것.

#### 해결 — 막지 않고 해석을 밝힌다 (A안)

| 표현 | 사용자의 의도 | 원하는 동작 |
|---|---|---|
| "여행 갈 때 쓰는 통장" | 계좌를 **설명** | 여행 자금으로 찾기 |
| "휴가비 계좌" | **이름**을 댔는데 그런 이름이 없음 | 잘못 알고 있을 수 있으니 확인 필요 |

LLM에게 이 차이를 완벽하게 구분시키기는 어렵다. 프롬프트를 엄격하게 하면(B안) "여행 갈 때 쓰는 통장"까지 막힐 수 있고, 실험에서 봤듯 LLM이 지킨다는 보장도 없다.

그래서 **LLM이 고른 이름이 사용자 말에 글자로 없으면**(띄어쓰기 무시) 뜻으로 추측한 것으로 보고, 답 앞에 **"'여행 자금' 계좌로 이해했어요."** 를 붙였다. State에 한 턴짜리 칸 `inferred`를 추가 (`understand`가 쓰고 `respond`가 읽음).

> Step 2에서 "LLM이 뽑은 표현이 원래 문장에 있는지 대조"는 **안전장치로는 뺐었다.** 이번엔 같은 확인을 **막는 용도가 아니라 알려주는 용도**로 썼다. 막으면 뜻으로 찾는 장점이 사라지지만, 알려주기만 하면 장점은 살고 위험은 줄어든다.
> 금융 앱에서 "시스템이 어떻게 이해했는지 보여주기"는 흔한 설계다 (이체 전에 받는 사람 이름을 다시 보여주는 것처럼).

확인 코드도 고쳤다 — **이어 묻기만 한 대화로, 나머지는 질문마다 새 대화로.** "휴가비"는 "`uncertain`이거나 해석을 밝히면 통과"로 기대값을 바꾸고, 뜻이 통하지 않는 "주식 계좌"를 추가했다.

#### 최종 실행 — 8/8 (Gemini 7회)

```
[OK  ] 노드가 조회 경로 3개뿐
[OK  ] 생활비랑 저축 잔액 보여줘 -> 계좌 잔액입니다. / - 생활비: 520,000원
[OK  ] 내 계좌 전부 보여줘 -> 계좌 잔액입니다. / - 생활비: 520,000원
[OK  ] 생활비 잔액 얼마야? -> 생활비 계좌 잔액은 520,000원입니다.
[OK  ] 여행 갈 때 쓰는 통장 잔액 알려줘 -> '여행 자금' 계좌로 이해했어요. / 여행 자금 계좌 잔액은 310,000원입니다.
[OK  ] 오늘 날씨 어때? -> 죄송해요, 그 요청은 도와드릴 수 없어요. 지금 할 수 있는 일: 계좌 조회, 즉시이체, 카드 일시 잠금
[OK  ] 휴가비 계좌 잔액 알려줘 -> '여행 자금' 계좌로 이해했어요. / 여행 자금 계좌 잔액은 310,000원입니다.
[OK  ] 주식 계좌 잔액 알려줘 -> 말씀하신 계좌를 찾지 못했어요. 이 중에서 골라 다시 말씀해 주세요: 생활비, 저축, 여행 자금, 비상금
결과: 8/8 통과
```

> 출력 맨 위에 Google SDK가 `Direct use of automatic function calling (AFC)...` 경고를 낸다. 우리 코드가 아니라 SDK 내부 권고이고 동작에는 영향 없음. 로그 설정을 정리할 때 숨긴다.

### 13. 문서 재구성 — 기획서가 너무 자주 바뀐다

**내 지적**: 기획서는 최초 기획인데 너무 자주 바뀌는 거 아닌가? 원래 이렇게 개발하나?

→ **맞는 지적이었다.** 처음 만들 때 "잘 안 바뀌는 문서"라고 해놓고, 설계 결정이 생길 때마다 기획서에 덧붙여서 하루에 여섯 번 넘게 고쳤다. intent·slot 규칙, 검증 두 층, 에러 구조, API 키 설정, 해석 밝히기는 전부 **"어떻게"(설계)** 인데 **"무엇을 왜"(기획)** 문서에 들어가 있었다.

**실무의 보편적인 문서 구성**

| 문서 | 실무 이름 | 담는 것 | 바뀌는 방식 |
|---|---|---|---|
| 기획서 | PRD (Product Requirements Document) | 무엇을 왜 — 목표, 범위, 비목표 | **고정.** 범위가 바뀔 때만, 변경 이력과 함께 |
| 설계서 | Design Doc | 어떻게 — 구조, 흐름, 데이터, 규칙 | 구현하면서 **자라남** (living document) |
| 결정 기록 | ADR (Architecture Decision Record) | 결정마다 상황·결정·대안·이유 | **추가만** |
| 개발일지 | Dev log | 날짜별로 무엇을 했나 | 세션마다 추가 |
| 구현계획 | Roadmap | 순서와 진행 상황 | 자주 |

> 설계 문서가 바뀌는 건 정상이다. 다만 **기획은 고정**해두고, 설계가 바뀔 때는 **무엇이 왜 바뀌었는지를 따로** 남기는 게 원칙이다. 한 문서를 계속 덮어쓰면 처음 계획이 사라진다.

**평가 기준 확인**: 과제 페이지를 다시 확인했는데 **점수표 형태의 평가 기준은 없다.** 제출물 5종이 사실상의 평가 대상이다. 그중 "최종 설계 자료"가 **"실제 구현에 맞게 갱신한 설계 자료와 초안에서 변경한 내용 및 이유"** 를 요구한다 — 초안과 최종을 **따로** 보겠다는 뜻인데, 기획서를 덮어써서 그 차이가 git 기록에만 남고 문서로는 보이지 않았다.

**재구성한 것**

| 문서 | 무엇을 |
|---|---|
| `docs/기획서.md` | 기획만 남김 (무엇을 왜, 목표·비목표, 범위, 향후 확장, 제출물). 맨 위에 **변경 이력 표** |
| `docs/설계서.md` (신규) | 기획서의 설계 내용을 옮김 + **State 칸 표** 추가 (명세의 "주요 State 필드와 변경 시점") |
| `docs/설계변경기록.md` (신규) | **FigJam 초안 → 최종**의 차이를 주제별로 (A: 초안 → v1 8건, B: 구현 중 변경 12건, C: 미정 4건). 각 항목에 개발일지 링크 |

**제출물과의 대응**

| 제출물 | 문서 |
|---|---|
| 설계 초안 | FigJam (AI 없이 직접 작성) |
| 최종 설계 자료 | 설계서 + 설계변경기록 |
| 실행 안내 | README (Step 9) |
| 회고 | 회고.md (마지막) |

> 개발일지와 설계변경기록은 둘 다 "왜"를 담지만 **정리 기준이 다르다.** 개발일지는 **날짜순**(그날 무슨 일이 있었나), 설계변경기록은 **주제별**(이 설계가 어떻게 바뀌어 왔나). 설계변경기록은 개발일지에 흩어진 결정을 모아 요약하고 자세한 건 링크한다.
> 포트폴리오에서 설계변경기록은 **판단 과정을 보여주는** 문서라 신입에게 차별화 포인트가 된다.

**이어서 만든 것 (세션 마무리)**

| 파일 | 무엇 | git |
|---|---|---|
| `docs/코드읽기가이드.md` | 학습용 인수인계서(온보딩 문서). 읽는 순서, 파일마다 핵심 코드·쓰인 개념 번호·**스스로 확인 질문**(= 평가·면접 예상 질문). Step 0~3 작성, 이후 Step마다 추가 | 올림 |

**함께 짚은 것 — 평가에서 "설명할 수 있어야 한다"**: 명세가 "각자 설계의 변경 이유와 최종 흐름 및 분기 조건을 설명할 수 있어야 한다", "각 단계에서 작성한 코드를 이해하고"를 요구한다. 코드 줄 단위 공부를 너무 뒤로 미루면 설명하기 어려워질 수 있으니, Step이 끝날 때마다 핵심 부분만이라도 같이 보는 시간을 두기로 한다.

## 용어 정리

| 용어 | 뜻 |
|---|---|
| **seed data** | 시스템을 처음 채우는 초기 데이터. 테스트를 같은 조건에서 반복하기 위한 기준점 |
| **작업용 복사본** | 원본을 복사해 실제로 고쳐 쓰는 파일 (`bank_data.json`) |
| **제약 조건** (constraint) | DB가 규칙을 어기는 저장을 거부하게 하는 설정. "저장하는 곳에서 막는다" |
| **예외 계층** | 에러를 부모-자식 구조로 만들어, 받는 쪽이 필요한 만큼만 자세하게 받게 하는 것 |
| **상속** | `class 자식(부모):` — 부모의 기능을 물려받음. 에러를 직접 만들 때 `Exception`을 물려받는다 |
| **`raise ... from e`** | 에러를 바꿔서 던질 때 원래 에러를 원인으로 함께 남기는 문법 |
| **lazy initialization** | 지연 초기화. 미리 준비하지 않고 처음 필요해지는 순간에 준비 |
| **atomic write** | 임시 파일에 다 쓴 뒤 한 번에 교체해서, 저장이 완전히 되거나 아예 안 되게 하는 방식 |
| **`fsync`** | file synchronize. 운영체제에게 메모리의 내용을 지금 당장 디스크에 쓰라고 명령 |
| **`cp949`** | 한국어 Windows의 기본 문자 인코딩. 인코딩을 안 적으면 이걸로 저장돼 다른 OS에서 깨짐 |
| **indent** | 들여쓰기. 숫자는 한 층당 공백 칸 수 |
| **`ensure_xxx`** | "xxx가 있게 만든다 — 있으면 그대로, 없으면 만든다"는 관용 이름 |
| **허용값 강제** | Structured Output에서 `Literal`로 LLM이 고를 수 있는 값을 목록 안으로 제한하는 것 |
| **`uncertain`** | 허용 목록에 넣어두는 "모르겠음" 선택지. 없으면 LLM이 억지로 하나를 고른다 |
| **`create_model`** | Pydantic 모델을 실행 중에 만드는 기능. 허용 목록이 데이터에서 올 때 쓴다 (Step 3) |
| **`@model_validator`** | Pydantic에서 여러 칸을 함께 보는 검사. 쓸 수 있지만 업무 검사는 코드에 둔다 |
| **확인 피로** (confirmation fatigue) | 확인을 너무 자주 받으면 사람들이 읽지 않고 "확인"만 누르게 되는 현상 |
| **경계 조건** (edge case) | 0개·1개·여러 개처럼 끝자락의 경우. 버그가 가장 많이 숨는 곳 |
| **fake LLM** | 미리 정한 답만 돌려주는 테스트용 가짜 모델 (`FakeListChatModel` 등) |
| **fail fast** | 문제가 있으면 나중에 엉뚱한 곳에서 터지게 두지 않고, 시작할 때 바로 분명한 메시지로 멈추는 것 |
| **`SHARED_ENV_FILE`** | 여러 프로젝트가 함께 쓰는 키 파일의 위치를 적는 이 프로젝트의 설정 이름 |
| **`add_messages`** | LangGraph의 메시지 전용 Reducer. 이어 붙이되 같은 메시지는 중복으로 쌓지 않고 교체 |
| **`thread_id`** | Checkpointer가 대화를 구분하는 이름. 같으면 같은 대화로 기억이 이어진다 |
| **`lru_cache`** | 함수 결과를 기억해두는 장치. 여기선 Gemini 모델을 한 번만 만들려고 씀 |
| **temperature** | LLM 답의 무작위성. 0이면 같은 입력에 최대한 같은 답 |
| **통제 실험** | 한 번에 하나만 바꿔서 원인을 가리는 방법. 여기선 히스토리만 없애고 나머지는 그대로 |
| **Jev / System One 모델** | 문장 대신 선택지와 확률만 돌려주는 모델 계열 (TypeSafe AI, 2026-09) |
| **PRD** | Product Requirements Document. 무엇을 왜 만드나를 담는 기획 문서. 잘 바뀌지 않음 |
| **Design Doc** | 어떻게 만드나를 담는 기술 설계 문서. 구현하면서 자라남 |
| **living document** | 계속 고쳐지며 현재 상태를 담는 문서 (설계서). 대신 바뀐 내용은 따로 기록 |
