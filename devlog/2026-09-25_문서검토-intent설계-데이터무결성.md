### 1. 구현 전 자기 검토 — 찾은 구멍 6개

기획서·구현계획을 쓴 뒤 바로 코드로 가지 않고, 한 번 더 검토했다.

| 심각도 | 문제 | 왜 문제인가 | 조치 |
|---|---|---|---|
| 🔴 | 실행 방식과 import 방식이 안 맞음 | Step 1 확인 명령은 `from src import ...`, Step 4 실행은 `python src/main.py` — 한쪽에서 `ModuleNotFoundError` | 실행 방식 A안으로 통일 (→ 2절) |
| 🔴 | intent 이름 목록이 어디에도 없음 | `understand`가 뱉는 이름과 `HANDLERS` 키가 한 글자라도 다르면 `KeyError`. 대화 중 `lock_card` / `lock_card_temp` 등 이름이 들쭉날쭉했음 | `src/intents.py`로 한 곳에 정의 (→ 4절) |
| 🟡 | "기준일 = 실제 날짜" 결정이 기획서에 빠짐 | 결정은 했는데 문서에 없으면 나중에 근거를 못 찾음 | 기획서 6장 "시간 기준" 추가 |
| 🟡 | Step 3 완료 기준이 틀림 | 조회 경로만 만드는 단계인데 "설계도 전체와 일치"를 요구 | "조회 경로 부분과 일치"로 수정 |
| 🟢 | 잔액과 거래 내역의 합이 안 맞음 | 이체 기능에 버그가 있는지, 데이터가 원래 이상한지 구분할 수 없게 됨 | 무결성 규칙 정의 후 데이터 재구성 (→ 8절) |
| 🟢 | 09-22 일지가 절반만 기록됨 | 환경 세팅·데이터 설계·4가지 결정이 빠져 있음 | 09-22 일지 보완 |

> 1·2번은 같은 종류의 문제다 — **두 곳이 서로 맞아야 하는데, 맞추는 규칙이 없다.**
> 실무에서는 이런 약속을 **contract**(계약)라고 부르고, 반드시 한 곳에만 정의한다.
> 설계 문서 리뷰에서 경력자가 제일 먼저 보는 것도 기능 설명보다 이런 "경계에서 주고받는 이름과 형식"이다.

### 2. 실행 방식 — A안

| | A안 (채택) | B안 |
|---|---|---|
| 실행 | `uv run python src/main.py` | `uv run python -m src.main` |
| `src/` 안 import | `from data_store import load` | `from src.data_store import load` |
| 모듈 단독 확인 | `uv run python src/data_store.py` | `uv run python -m src.data_store` |
| 장점 | 강의에서 배운 `uv run main.py`와 같은 모양. 새 개념 없음 | 대형 프로젝트에서 더 흔함 |
| 단점 | 나중에 pytest를 쓸 때 설정 한 줄 필요 | `-m` 옵션과 패키지 개념을 새로 배워야 함 |

**채택 이유**: 지금 목적은 LangGraph 구조를 익히는 것이라 import 규칙에 시간을 쓰지 않는다.
A안의 단점은 `pyproject.toml`에 `pythonpath = ["src"]` 한 줄이면 해결된다.

**왜 두 방식이 다르게 동작하나**: `python src/main.py`로 실행하면 파이썬은 **실행한 파일이 있는 폴더(`src/`)** 를 기준으로 모듈을 찾는다. 그래서 `src/` 안의 파일끼리는 폴더 이름 없이 부른다.

각 모듈은 맨 아래에 확인 블록을 둬서 단독으로 돌려볼 수 있게 한다.

```python
# 직접 실행했을 때만 돌아가는 확인 코드 (다른 파일에서 import 할 때는 실행 안 됨)
if __name__ == "__main__":
    main()
```

### 3. "intent"는 표준 용어다

챗봇·음성비서 분야에서 사용자 말을 해석할 때 쓰는 용어 두 개.

| 용어 | 뜻 | 이 프로젝트에서 |
|---|---|---|
| **intent** (의도) | 사용자가 **무엇을 하려는가** | `transfer_instant` |
| **slot** / entity (값) | 그 일에 **필요한 정보** | 출금 계좌, 입금 계좌, 금액 |

Dialogflow, Rasa 같은 챗봇 도구가 쓰는 용어다. 우리 State의 `params` 필드가 원래 이름으로는 **slot**에 해당한다.
이름을 `slots`로 바꿀 필요는 없지만, 면접에서 "intent 분류 + slot 채우기 구조"라고 설명할 수 있다.

### 4. intent 목록은 코드 한 곳에 — Single Source of Truth

**질문**: intent 이름을 따로 문서로 정리할까, 키-값처럼 매칭해둘까?

**결론**: 둘 다 하되 **원본은 코드 한 곳**. 문서에만 적으면 코드가 바뀌어도 문서가 저절로 따라 바뀌지 않아서, 몇 주 뒤엔 아무도 문서를 믿지 않게 된다.

```python
# src/intents.py (일부) — intent 이름의 유일한 정의처
INTENTS = {
    "account_list_with_balance": {
        "desc": "계좌 목록과 잔액 조회. 계좌를 지정하면 그 계좌만 보여준다",
        "kind": "read",                  # read = 조회, write = 변경
        "required": [],                  # 없으면 되물어야 하는 slot
        "optional": ["account"],         # 없어도 실행되는 slot
    },
    # transfer_instant, card_lock_temporary 도 같은 모양으로 들어 있음
}

# 표에서 자동으로 뽑아낸다 → 손으로 따로 관리하지 않는다
READ_INTENTS = frozenset(name for name, info in INTENTS.items() if info["kind"] == "read")
WRITE_INTENTS = frozenset(name for name, info in INTENTS.items() if info["kind"] == "write")
```

이 표를 네 곳이 **가져다 쓴다.**

| 가져다 쓰는 곳 | 무엇을 가져가나 |
|---|---|
| `understand`의 프롬프트 | "이 중에서 골라라"는 선택지 |
| Pydantic 스키마 | 허용되는 intent 값 |
| `route_request` | 조회냐 변경이냐 (`READ_INTENTS`) |
| `HANDLERS` | 변경 intent마다 Handler가 있는지 |

> 09-22에 본 `HANDLERS` 레지스트리("if문 대신 표에서 찾기")를 한 단계 확장한 것이다. 새 개념이 아니라 응용.
> `READ_INTENTS`를 손으로 적지 않는 게 포인트다. 손으로 적으면 새 조회 기능을 추가할 때
> 두 곳을 고쳐야 하고, 한 곳을 빠뜨리면 조회 요청이 승인 경로로 새어 들어간다.

`required`를 여기 두기로 했으므로, **Handler 클래스에는 `required`를 다시 적지 않는다.** 09-22 일지의 Handler 예시 코드에 있던 `required = [...]` 줄은 빠진다.

실행 확인 (`src/` 폴더에서):

```
read: ['account_list_with_balance']
write: ['card_lock_temporary', 'transfer_instant']
```

### 5. intent 이름 — 더 구체적으로

처음 제안한 이름에 대한 지적.

| 처음 이름 | 지적 | 새 이름 |
|---|---|---|
| `list_accounts` | 목록인 건 알겠는데 **잔액까지** 보여준다는 게 안 드러남 | `account_list_with_balance` |
| `transfer` | 즉시·조건부·분할 중 **어느 이체인지** 모름. 2차에 바로 막힘 | `transfer_instant` |
| `lock_card` | 일시 잠금인지 분실 정지인지 **이름만으로 모름** | `card_lock_temporary` |

**규칙: `대상_동작_세부`**

대상을 맨 앞에 두면 **알파벳순 정렬만으로 같은 업무끼리 모인다.** 2차·3차까지 붙였을 때:

```
account_list_with_balance    ┐ 계좌
account_total_balance        ┘

bill_list_unpaid             ┐
bill_pay                     │ 청구서
bill_pay_all                 ┘

card_lock_temporary          ┐
card_report_lost             │ 카드
card_unlock                  ┘

transfer_conditional         ┐
transfer_instant             │ 이체
transfer_split               ┘
```

동작을 앞에 두면(`lock_card_temporary`, `list_accounts` ...) 카드 관련 기능이 목록 여기저기로 흩어진다.

`temporary`를 `temp`로 줄이지 않은 이유: `temp`는 temperature(온도)로도 읽힌다. 이름이 조금 길어져도 **줄임말로 오해가 생기지 않게** 하는 게 실무 기준.

Handler 클래스 이름은 intent 이름을 **PascalCase**(단어 첫 글자를 대문자로 붙여 쓰기)로 바꾼 것으로 통일: `TransferInstantHandler`, `CardLockTemporaryHandler`.

### 6. 왜 계좌 목록과 잔액 조회가 하나의 intent인가

**출처**: 과제 명세의 "계좌 조회" 한 줄이 목록과 잔액을 함께 정의하고, 내 기능 정리 문서도 같다.

**나누는 기준**

> **처리 방식이 다르면 → intent를 나눈다**
> **처리는 같고 대상만 다르면 → 같은 intent에 slot으로 구분한다**

| 사용자 문장 | 처리 | 판단 |
|---|---|---|
| "내 계좌 목록 보여줘" | 내 계좌를 목록으로 | `account_list_with_balance` |
| "내 계좌 목록과 잔액 보여줘" | 같음 | 같음 |
| "생활비 잔액 얼마야?" | 같은 처리, 생활비만 | 같은 intent + `account="생활비"` |
| "내 계좌에 총 얼마 있어?" | **더하는** 처리 추가 | 별도 intent (2차) |

**나누면 생기는 문제**: `account_list`와 `account_balance`로 나눴다면 명세 예시 문장 "내 계좌 목록과 잔액을 보여줘"는 **둘 다에 해당한다.** `understand`가 하나를 골라야 하는데 실행할 때마다 흔들릴 수 있다.

> intent 설계의 기본 원칙이 **상호 배타성**(한 문장은 하나의 intent에만 속한다)이다.
> 09-22에 본 "아니, 5만 원만"이 거절로 오분류되는 문제와 같은 종류 — **분류 대상의 경계가 겹치면 오분류가 생긴다.**
> 실제 은행 앱도 계좌 목록 화면에는 항상 잔액이 같이 나온다.

### 7. slot이란 — 값을 담는 빈칸

**처음 오해**: "특정 계좌를 말하면 slot을 만들어준다", "slot은 메서드 같은 건가?"

**정리**: slot은 메서드가 아니라 **값이 들어갈 빈칸**이다. 영어 slot은 "끼워 넣는 홈, 자리"(동전 넣는 구멍 = coin slot).

이체 신청서로 비유하면:

```
┌─────── 이체 신청서 ───────┐   ← 신청서 종류 = intent
│ 출금 계좌: [__________]   │   ← slot
│ 입금 계좌: [__________]   │   ← slot
│ 금액:      [__________]   │   ← slot
└───────────────────────────┘
사용자 말에서 값을 뽑아 빈칸을 채우는 일 = slot filling (understand 노드가 하는 일)
```

파이썬 함수로 옮기면 intent는 **함수 이름**, slot은 **매개변수**다.

```python
def account_list_with_balance(account=None):             # 기본값 있는 매개변수 = 선택 slot
    ...                                                   # 내 계좌를 읽고, account가 있으면 그것만 남김

def transfer_instant(from_account, to_account, amount):   # 기본값 없는 매개변수 = 필수 slot
    ...                                                   # 이체 처리
```

| intent 용어 | 파이썬 용어 |
|---|---|
| intent | 함수 이름 |
| slot | 매개변수 |
| 필수 slot | 기본값이 **없는** 매개변수 — 안 주면 실행 불가 |
| 선택 slot | 기본값이 **있는** 매개변수 — 안 주면 기본값으로 동작 |

**흐름으로 보면**

```
"생활비 잔액 얼마야?"
    ↓ understand (slot filling)
intent = "account_list_with_balance",  params = {"account": "생활비"}
    ↓ read_task
account_list_with_balance(account="생활비")  → 생활비 계좌 1개

"내 계좌 보여줘"
    ↓ understand
intent = "account_list_with_balance",  params = {}      ← 선택 slot이라 비어도 괜찮음
    ↓ read_task
account_list_with_balance()                  → 계좌 4개 전부
```

**"slot을 만든다"가 아니다** — 역할이 셋으로 나뉜다.

| 무엇 | 어디에 | 종류 |
|---|---|---|
| "이 intent에는 `account` 빈칸이 있다" | `src/intents.py` | **정의** (한 번 적어둠) |
| "이번 문장에서 `account`는 생활비" | State의 `params` | **값** (매번 바뀜) |
| "`account`가 있으면 그 계좌만 걸러낸다" | `src/functions.py` 함수 본문 | **코드** (한 번 짜둠) |

"메서드 같은 건가?"라고 느낀 건 세 번째(걸러내는 코드) 때문이었다. 그건 맞지만, 그 코드는 조회 함수 안에 있고 slot은 그 함수에 넘기는 값일 뿐이다.

**필수/선택 구분이 그래프의 루프 1을 정한다.** `understand`가 적는 `missing`의 정확한 정의가 **"채워지지 않은 필수 slot"** 이다.
"저축으로 10만 원 옮겨줘"는 필수 slot `from_account`가 비어서 `ask_more`로 가고, "내 계좌 보여줘"는 선택 slot만 비어서 그냥 실행된다.

**slot에는 ID가 아니라 사용자가 말한 표현이 들어간다.** 그래서 카드 slot 이름은 `card_id`가 아니라 `card`다.

```
"생활비 카드 잠가줘"  →  params = {"card": "생활비 카드"}   사용자가 말한 그대로
                         ↓ plan_change에서
                         "생활비 카드" → card_001           ID로 변환
```

곧바로 ID로 바꾸지 않는 이유는 "생활비"처럼 **후보가 여러 개일 수 있기 때문.** 변환하는 단계에서 후보를 세어보고, 여러 개면 되묻는다.

### 8. 초기 데이터 무결성

**발견**: 생활비 계좌의 거래를 다 더해도 잔액 520,000원이 나오지 않았다. 거래 20건은 "일부만 보여주는 샘플"이라고 생각했지만, **데이터도 무결성 검증에 맞아야 한다.**
데이터가 처음부터 틀려 있으면 나중에 이체 기능에 버그가 있는지, 데이터가 원래 이상한지 **구분할 방법이 없다.**

#### 규칙 정의 — 0원 시작

"모든 계좌가 0원에서 시작했다"는 가정을 택했다. **실제 계좌도 개설 직후 잔액은 0원**이기 때문.
대안이었던 "계좌마다 기초 잔액(이월) 거래를 하나 두기"는 택하지 않았다.

| # | 규칙 |
|---|---|
| 1 | 계좌 잔액 = 입금 합계 − 출금 합계 (0원 시작) |
| 2 | 시간순으로 따라가도 잔액이 음수가 된 적 없음 |
| 3 | 거래의 소유자 = 그 계좌의 소유자 |
| 4 | 카드 결제는 그 계좌에 연결된 카드로만 |
| 5 | ID 중복 없음, 가리키는 대상이 실제로 존재 |
| 6 | 금액은 0보다 큰 정수(잔액은 0 이상), 거래 유형은 `deposit` / `withdrawal` |
| 7 | 기준 시각보다 미래의 거래 없음 |

**처음 제안에 있다가 뺀 규칙**: "계좌 간 이체는 출금 1건 + 입금 1건이 짝을 이룬다."
코드로 옮기다 보니 **현재 거래 구조로는 검사가 불가능**했다. 월세 같은 외부 출금과 내 계좌로의 이체 출금이 기록상 똑같이 생겼다(`card_id`, `merchant` 모두 `null`).
→ 즉시이체를 구현할 때(Step 5) 거래에 상대 계좌를 기록할지 결정한다.

그 대신 "미래 거래 없음"이 추가되었다. 기준일을 실행 시점의 실제 날짜로 정했으니 필요해진 규칙.

#### 검사는 눈이 아니라 코드로 — `src/integrity.py`

파일 이름: integrity = **무결성.** 데이터베이스 분야에서 "데이터가 규칙에 맞게 온전한 상태"를 가리키는 표준 용어.
처음엔 `scripts/validate_data.py`로 하려 했지만, 나중에 **이체 후 장부 검사**에도 재사용할 거라 `src/` 안에 뒀다.

```python
# src/integrity.py 의 핵심 부분 — 거래를 시간순으로 따라가며 계좌별 잔액을 0원부터 쌓는다
running = defaultdict(int)   # 계좌별 누적 잔액. 처음엔 전부 0원
for tx in sorted(data["transactions"], key=lambda t: datetime.fromisoformat(t["occurred_at"])):
    ...                      # 규칙 3·4·5·6·7 검사 (소유자, 카드-계좌 연결, ID, 값, 미래 거래)
    running[tx["account_id"]] += tx["amount"] if tx["type"] == "deposit" else -tx["amount"]
    if running[tx["account_id"]] < 0:
        ...                  # 규칙 2 위반 기록 (잔액이 음수가 됨)

# 규칙 1 — 쌓아서 계산한 잔액이 저장된 잔액과 같은가
for acc_id, account in accounts.items():
    if running[acc_id] != account["balance"]:
        ...                  # 규칙 1 위반 기록
```

```bash
uv run python src/integrity.py                      # 원본 검사
uv run python src/integrity.py data/bank_data.json  # 작업용 복사본 검사
```

실패하면 종료 코드 1을 돌려준다. 다른 도구(나중에 CI 등)가 실패를 알아챌 수 있게.

#### 빨간불을 먼저 봤다 (red first)

데이터를 고치기 **전에** 검사기부터 돌렸다.

```
결과: 5/7 통과 (initial_data.json)
[FAIL] 1. 계좌 잔액 = 입금 합계 - 출금 합계 (모든 계좌는 0원에서 시작)
[FAIL] 2. 시간순으로 따라가도 잔액이 음수가 된 적 없음
```

예: 여행 자금 계좌는 입금 기록 없이 대한항공 150,000원 결제부터 시작해서, 0원 시작 기준으로 바로 −150,000원이 된다.

> 고친 데이터로만 돌려보면, 검사기가 무조건 "통과"만 뱉는 버그가 있어도 알아챌 수 없다.
> **실패해야 할 때 실패하는 걸 봐야 검사기를 믿을 수 있다.** 테스트 주도 개발(TDD)의 첫 단계와 같은 발상.
> 그래서 커밋도 "검사기 추가(5/7)" → "데이터 보정(7/7)" 순서로 나눴다.

#### 재구성 — 잔액은 그대로, 거래를 다시 짬

| 계좌 | 들어온 돈 | 나간 돈 | 잔액 |
|---|---|---|---|
| 생활비 (user_01) | 급여 2,500,000 + 부수입 800,000 | 월세 700,000 · 카드 결제 13건 420,000 · 다른 계좌로 이체 4건 1,660,000 | **520,000** |
| 저축 | 첫 입금 750,000 + 생활비에서 이체 2건 1,100,000 | — | **1,850,000** |
| 여행 자금 | 생활비에서 이체 460,000 | 대한항공 150,000 | **310,000** |
| 비상금 | 생활비에서 이체 100,000 | 출금 25,000 | **75,000** |
| 생활비 (user_02) | 급여 500,000 | 카드 결제 2건 70,000 | **430,000** |

- **거래 20건 → 30건**: 각 계좌의 첫 입금, 그리고 계좌 간 이체의 **입금 쪽 기록**이 새로 필요했다 (이체 1번 = 출금 1건 + 입금 1건)
- **거래 ID를 시간순으로 다시 매김**: `tx_001`이 가장 오래된 거래
- **테스트용 상황 유지**: 잔액 5개 그대로, 5만원 이상 카드 결제 5건, 스타벅스 2건

```
결과: 7/7 통과 (initial_data.json)
종료 코드: 0
```

#### 시간대 처리

`ZoneInfo("Asia/Seoul")` 대신 `timezone(timedelta(hours=9))`를 썼다.
Windows에는 시간대 데이터베이스가 기본으로 없어서 `ZoneInfo`가 실패할 수 있고, 한국은 서머타임이 없으므로 "항상 +9시간" 고정 오프셋으로 충분하다.

## 헷갈렸던 것 / 배운 것

| 헷갈렸던 것 | 바로잡은 내용 |
|---|---|
| "intent"라는 명칭을 실제로 쓰나? | **쓴다.** 챗봇·음성비서 분야의 표준 용어. `params`는 원래 이름으로 slot |
| slot은 메서드인가? | **아님.** 값을 담는 빈칸 = 함수의 **매개변수**. 거르는 코드가 함수 쪽 |
| 특정 계좌를 말하면 slot을 만들어주나? | **아님.** 빈칸은 `intents.py`에 미리 정의되어 있고, 말할 때마다 **값만** 채워진다 |
| 목록과 잔액은 왜 합쳐져 있나? | 처리가 같기 때문. 나누면 "목록과 잔액 보여줘"가 두 intent에 겹친다 |
| 데이터는 샘플이니 합이 안 맞아도 되나? | **안 된다.** 틀린 데이터 위에서는 이체 버그를 구분할 수 없다 |
| 검사기는 통과만 확인하면 되나? | **실패하는 걸 먼저 봐야** 검사기를 믿을 수 있다 |

## 용어 정리

| 용어 | 뜻 |
|---|---|
| **intent** | 사용자가 무엇을 하려는가 (의도). 신청서의 종류 |
| **slot** | 그 일에 필요한 정보가 들어갈 빈칸. 함수의 매개변수에 해당 |
| **slot filling** | 사용자 말에서 값을 뽑아 빈칸을 채우는 일. `understand` 노드의 역할 |
| **Single Source of Truth** | 같은 정보를 여러 곳에 적지 않고 한 곳에서만 관리하는 원칙 |
| **contract** (계약) | 두 코드가 주고받는 이름·형식에 대한 약속. 한 곳에만 정의해야 함 |
| **상호 배타성** (mutually exclusive) | 한 문장은 딱 하나의 intent에만 속해야 한다는 원칙 |
| **PascalCase** | 단어 첫 글자를 대문자로 붙여 쓰는 방식 (`TransferInstantHandler`). 파이썬 클래스 이름 관례 |
| **frozenset** | 한 번 만들면 바꿀 수 없는 집합. 실행 중 실수로 추가·삭제되는 것을 막음 |
| **integrity** (무결성) | 데이터가 규칙에 맞게 온전한 상태 |
| **red first** | 통과시키기 전에 먼저 실패하는 걸 확인하는 것. TDD의 첫 단계 |
| **TDD** | Test-Driven Development. 실패하는 테스트를 먼저 만들고 코드로 통과시키는 개발 방식 |
| **대사** (reconciliation) | 장부와 실제 잔액을 맞춰보는 작업. `integrity.py`의 규칙 1이 이것 |
| **고정 오프셋** | 서머타임 없이 항상 같은 시차(+9시간)를 쓰는 시간대 표현 |
| **종료 코드** (exit code) | 프로그램이 끝날 때 돌려주는 숫자. 0 = 성공, 그 외 = 실패 |
