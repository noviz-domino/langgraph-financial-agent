## TL;DR

1. 교수님 피드백: `respond` 안에 if문과 문장이 너무 많으니 **상수로 올리면 좋겠다.** 문장을 함수 안에 박아 두면 어떤 안내가 있는지 보려고 함수를 따라 읽어야 한다.
2. 그래프 공통 문장 21개를 `graph.py` 위쪽 "안내 문장" 블록으로, 웹 오류 문장 4개를 `web.py` 위쪽으로 올렸다. `respond`는 표에서 찾기만 한다. **사용자가 보는 문장은 한 글자도 바뀌지 않았다** (50개 비교).
3. 멀티 에이전트로 나누지 않는 이유를 B30과 설계서 2장에 적었다. 9/29·9/30에 한 일 중 설계서에 빠져 있던 것(웹 입구, 바쁠 때 대응, 여러 요청)도 채웠다.

## 가독성 정리 (교수님 피드백)

**무엇을 올렸나**

| 위치 | 전 | 후 |
|---|---|---|
| `graph.py` `respond` | if/elif 12갈래에 문장이 섞여 있음 | `INTENT_REPLIES`(처리 불가·이해 실패·여러 업무·바쁨), `DECISION_REPLIES`(그만둠·취소·수정 초과·만료) 표에서 찾기 |
| `graph.py` `_question`·`ask_more`·`confirm_change`·`apply_change` | 노드마다 문장이 흩어져 있음 | `ASK_*`, `CONFIRM_*`, `APPLY_*` 상수 |
| 예시 문장 "생활비에서 저축으로 10만 원 보내줘" | `graph.py` 2곳, `main.py` 1곳에 따로 | `EXAMPLE_REQUEST` 하나 |
| `web.py` HTTP 오류 | `raise` 줄 안에 문장 | `SESSION_EXPIRED` 등 상수 4개 |
| `decision` 값 8종 | 문자열로만 주고받음 (허용 값 목록 없음) | State에 `Literal`로 선언 (`Decision`, `Answer`) |

**정한 것**

| 정한 것 | 결정 | 이유 |
|---|---|---|
| 상수를 어디에 | 쓰는 파일 위쪽 (`graph.py`, `web.py`). 새 파일(`messages.py`)은 만들지 않음 | 그 문장을 쓰는 코드와 같은 파일에 있어야 찾기 쉽다. 파일 하나에 모으면 오히려 왔다 갔다 해야 한다 |
| 업무별 문장 | 그대로 `functions.py`의 Handler 옆 | "업무를 추가할 때 표 한 줄 + Handler 하나로 끝낸다"는 원칙 — 업무 문장은 그 업무와 함께 있어야 한다 |
| 그대로 둔 것 | Pydantic `description`, 무결성·저장·설정의 오류 메시지, 자체 확인 블록 문자열 | 칸 정의나 진단 맥락 바로 옆에 있어야 읽힌다. 한 번씩만 쓰인다 |
| 상태 값 | 문자열을 상수로 바꾸지 않고 `Literal`로 허용 값만 선언 | `"approve"`처럼 문자열 그대로가 더 읽기 쉽다. 오타는 편집기가 허용 값 목록으로 잡는다 |
| `respond`의 순서 | 원래 순서 유지 (intent → 그만둠 → 되묻기 한도 → 승인 결과) | if/elif는 위에서부터 먼저 걸리는 게 이긴다. 표로 바꿔도 우선순위가 바뀌면 안 된다 |

**확인**

- 리팩터링 **전에** 가짜 LLM으로 23개 흐름(처리 불가·되묻기·후보 고르기·승인·취소·수정·수정 초과·만료·실행 직전 잔액 변화·저장 실패·이어받은 계좌·웹 오류 등)을 돌려 사용자가 보는 문장 50개를 저장해 두고, 바꾼 **뒤에** 같은 흐름으로 비교 → **모두 같음**
- 그래프 모양(Mermaid 출력) 전후 같음, `evaluation.py --offline` 8/8, `integrity.py` 10/10, 작업용 복사본은 전후 그대로
- `functions.py` 자체 확인이 26/31 — 바꾸기 전에도 같았다. 이 확인은 작업용 복사본을 읽는데, 직접 써 보면서 잔액이 바뀌어 있어서 원본 잔액을 기준으로 짠 5개가 걸린다. 리팩터링과는 무관 → 아래 "자체 확인이 원본을 읽게"에서 고침

## 자체 확인이 원본을 읽게 (`functions.py`)

코드가 틀린 게 아니라 **확인이 엉뚱한 장부를 봤다.** 기대값은 원본 기준(생활비 520,000원 → 10만 원 보내면 420,000원)인데 읽는 건 작업용 복사본이라, `main.py`로 이체를 한 번만 해 봐도 실패했다.

| 정한 것 | 결정 | 이유 |
|---|---|---|
| 무엇을 읽나 | 원본(`initial_data.json`)을 읽기만 | 이 확인은 원래 "읽기만 하고 바꾸는 확인은 복사한 dict에서"라 원본을 읽어도 원본은 안 바뀐다 |
| `reset()`으로 복사본을 되돌리는 방법 | 쓰지 않음 | 직접 써 본 장부가 지워진다 (`scenarios.py`는 그렇게 하므로 돌리면 지워진다고 적어 둠) |

- 확인: 31/31, 원본·작업용 복사본 모두 전후 그대로

## 멀티 에이전트로 나누지 않는 이유 (B30)

강의 예제(Supervisor + 담당 에이전트)를 보고 우리는 왜 하나인지 정리했다. 처음부터 그래프 하나로 설계했지만 이유를 적지 않았었다 → [설계서 2장 "에이전트는 하나"](../docs/설계서.md), [설계변경기록 B30](../docs/설계변경기록.md)

- 에이전트를 나누는 것 = **절차를 따로 두는 것.** 세 업무는 절차가 같고 다른 건 검증·실행 코드뿐이라 Handler로 충분
- 나누면 승인 장치가 담당마다 생기고(하나만 빠져도 사고), LLM 호출이 늘고, 조회 → 이체로 이어지는 상태를 담당끼리 넘겨야 한다
- 굳이 나눈다면 업무가 아니라 **분야** 단위(라우터 + 계좌 담당 + 카드 담당). LLM은 라우터에만, 승인 흐름은 공유. 실제 은행처럼 분야와 조직이 많아지면 나누는 게 맞다

## 설계서 보완

9/29·9/30에 한 일이 설계서에 빠져 있었다.

- 2장에 **웹 입구** 절 — API 3개, 공개하면 생기는 문제와 장치(방문자별 장부, 호출 제한, 입력 길이, 중복 클릭, 세션 만료)
- LLM 절에 **재시도·시간 제한**, 실패 구분(`llm_busy`), **한 말에 여러 업무**, 수정 중 실패
- 폴더 구조에 `web.py`, `studio.py`, `evaluation.py`, `web/index.html`, `data/ledgers/`
- 변경 이력을 날짜순(최신이 위)으로 다시 정렬하고 빠진 4줄 추가

기획서는 고치지 않았다. 웹 화면은 비목표였지만 `feat/web` 브랜치에서 포트폴리오용으로 더한 것이라 과제 제출본(`main`)의 범위는 그대로다. `main`에 합치면 그때 범위가 바뀐 것으로 고친다.

## 배운 것

- 리팩터링은 "동작이 안 바뀌었다"를 **먼저 증명할 방법**을 만들고 시작한다. 바꾸기 전 출력을 저장해 두고 바꾼 뒤 비교하면, 문장 50개를 눈으로 대조하지 않아도 된다.
- 상수로 올릴 것과 둘 것의 기준은 "**누가 함께 고치나**"다. 그래프 공통 문장은 말투를 맞추며 한꺼번에 고치니 모으고, 업무별 문장은 그 업무와 함께 고치니 업무 옆에 둔다.
- 문자열로 주고받는 상태 값은 허용 값을 한 곳에 선언해 두지 않으면 오타가 에러 없이 다른 분기로 빠진다.
