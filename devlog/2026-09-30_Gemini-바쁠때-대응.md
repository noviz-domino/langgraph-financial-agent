# 개발일지 2026-09-30 — Gemini가 바쁠 때 대응

| 항목 | 내용 |
|---|---|
| 세션 주제 | 공개한 웹 화면에서 Gemini 무료 등급의 503·지연에 대비 |
| 결과물 | 수정 3건(바쁠 때 대응, 호출 제한 강화, 여러 요청 안내), 설계변경 B26, 서버 재배포, 설계 판단 정리 B27(미들웨어·LangGraph), LangSmith 평가 실험 2건 |
| 이전 일지 | [2026-09-29 직접 써 보기](2026-09-29_직접-써보기.md) |

---

## TL;DR

1. Gemini 무료 등급은 사용자가 몰리면 **503(과부하)을 주거나 답이 늦다.** 그런데 화면에는 "요청을 이해하지 못했어요"가 나왔다 — 사용자 잘못이 아닌데 다시 말하라고 한 셈.
2. SDK 기본값이 **6번까지 다시 보내서** 바쁠 때 1분 넘게 "…"로 멈춰 있을 수 있었다.
3. **20초 제한 + 총 2번 시도**로 줄이고, 서버 쪽 실패는 "지금 AI 서버가 바빠요. 잠시 후 같은 말을 다시 보내 주세요."로 따로 안내한다 (B26).

---

## 정한 것

| 정한 것 | 결정 | 이유 |
|---|---|---|
| 재시도를 어디서 | SDK 설정(`max_retries=2`, `timeout=20`) | SDK가 이미 503·429에 기다렸다 다시 보내는 기능이 있다. 직접 반복문을 만들 필요가 없다 |
| 몇 번 | 처음 1번 + 재시도 1번 | 잠깐 몰린 경우는 한 번이면 대부분 풀린다. 더 기다리게 하기보다 빨리 알려 준다 (최대 약 40초) |
| 실패 구분 | `is_retryable`이 참이거나 시간 초과면 `llm_busy`, 그 밖은 `not_understood` | "다시 보내면 될 수 있는 오류"를 LangChain이 이미 표시해 둔다. 오류 문구로 가르지 않는다 |
| 승인 화면의 수정 요청 중 실패 | 그대로 둠 (승인 대기 요청 유지, '예/취소' 안내) | 요청을 잃지 않는 게 먼저. 문구 구분은 필요해지면 |

- `max_retries`는 이름과 달리 **총 시도 횟수**다 (SDK 설명: 재시도를 끄려면 0이 아니라 1)

## 확인

- Gemini 호출 없이 가짜 오류 5종으로 확인: 503·429·시간 초과 → "바빠요", 400·형식 오류 → "이해하지 못했어요"
- 서버에 다시 배포: 서비스 `active`, 시작 로그에 오류 없음

## 호출 제한 강화

무료 등급 한도 안에서 여러 방문자가 나눠 쓰도록 제한을 줄였다.

| | 전 | 후 |
|---|---|---|
| 방문자마다 | 10분에 30번 | **1분에 3번 + 10분에 10번** (둘 중 하나라도 넘으면 429) |
| 서버 전체 | 하루 500번 | **하루 50번** |
| 한 번에 보내는 글자 | 300자 | 그대로 |

- 1분 제한은 연달아 누르는 것을, 10분 제한은 오래 붙잡고 쓰는 것을 막는다. 요청 시각 목록 하나로 두 구간을 함께 센다
- 가짜 시계로 확인: 1분 안 4번째 막힘·1분 뒤 다시 됨, 50초 간격 11번째 막힘, 하루 51번째 막힘
- 하루 횟수는 메모리에만 있어서 **서버를 재시작하면 0부터 다시 센다** (알고 둔다)

## 미들웨어를 쓰지 않은 이유 정리 (B27)

호출 제한을 만들고 나서 "이런 공통 검사는 미들웨어로 하는 것 아닌가?"가 궁금해져 정리했다. 코드는 바꾸지 않았다.

**미들웨어란**: 요청이 업무 코드에 닿기 전·후에 **프레임워크가 자동으로 실행하는** 공통 코드. 건물 입구의 경비실과 같다. 함수로 만들어 재사용하는 것과 달리, 개발자가 호출하지 않아도 **모든 요청에 빠짐없이** 걸린다는 게 핵심이다 (인증처럼 빠지면 사고가 나는 것에 쓴다).

| 층 | 미들웨어 | 우리 |
|---|---|---|
| FastAPI (웹) | `@app.middleware`, `add_middleware` | 안 씀 — `/api/chat` 안에서 `_check_limits()` 직접 호출 |
| LangChain `create_agent` | `middleware=[...]` (모델·도구 호출 앞뒤) | 안 씀 — `create_agent` 자체를 안 씀 |
| LangGraph | 개념 없음 (노드·엣지로 직접 표현) | 이걸 씀 |

- **웹**: Gemini를 부르는 엔드포인트가 하나라 빼먹을 위험이 없다. 세션 ID가 요청 본문에 있어서 미들웨어로 옮기면 오히려 복잡해진다. 엔드포인트가 늘면 그때 옮긴다
- **`create_agent`**: LangGraph로 미리 만든 ReAct 그래프(모델 ⇄ 도구 반복)다. 코딩 에이전트처럼 **LLM이 몇 번 돌지 정하는** 자율형이라 루프를 바깥에서 통제할 미들웨어가 필요하다. 우리는 순서가 고정이고 LLM은 `understand` 한 곳뿐이라 필요 없다
- **왜 체인이 아니라 LangGraph**: 고정 순서여도 한 줄이 아니다 — 승인 화면에서 **멈췄다가 다음 턴에 이어서**(`interrupt` + checkpointer), **여러 겹의 갈림길**, 수정 요청 시 **되돌아가기**가 있다

## 한 번에 여러 요청 (B28)

배포한 사이트에서 직접 써 봤다. 미래에 넣을 돈을 핑계로 잔액보다 큰 이체를 시켜 봤는데, 잔액 검사는 지금 장부만 보므로 둘 다 거절됐다. 그런데 **"A→B 1000만 원, 그리고 B→A 1000만 원"에서 뒤의 이체가 말없이 사라졌다.**

| 정한 것 | 결정 | 이유 |
|---|---|---|
| 여러 업무를 받으면 | 아무것도 실행하지 않고 하나씩 말해 달라고 안내 | 앞의 것만 처리하면 나머지도 된 줄 안다. 차례로 처리하면 승인·되묻기가 여러 개 얽힌다 |
| 누가 판단하나 | `understand`의 LLM이 칸(`multiple`) 하나 더 채움 | 뜻을 알아야 판단할 수 있다. 호출은 늘리지 않는다 |
| 조회 대상 여럿 | 업무 하나 | "생활비랑 저축 잔액"은 한 번에 보여 줄 수 있다 |
| 승인 화면에서 수정 중에 여러 업무 | 기다리던 요청 유지 | 요청을 잃지 않는 게 먼저 (바쁠 때 대응과 같은 원칙) |

- 확인 (Gemini 5회): 이체 두 번·이체와 카드 잠금 → 안내, 계좌 두 개 조회·이체 한 건·"좀 있다 넣을게" 이체 → 평소대로

## LangSmith 평가 실험 (강의 30번 적용)

강의(LangGraph Agent 평가)에서 배운 **Dataset → target → evaluator → Experiment**를 우리 Agent에 작게 적용해 봤다. 실험용 스크립트는 프로젝트 밖에 두고, 프로젝트 코드는 바꾸지 않았다.

**먼저 정리한 것**

- `scenarios.py`가 이미 평가다. 질문과 기대값을 짝지은 사례(Golden set), 채점(`lambda` 검사), 승인 절차·장부 확인, 사례 격리(`thread_id`, `reset()`)가 있다. 없던 것은 **결과를 LangSmith Experiment로 남기는 형식**뿐
- **Tracing과 Evaluation은 다르다.** API 키와 `LANGSMITH_TRACING=true`면 실행 기록(Trace)은 자동으로 쌓인다. 하지만 "맞았나"는 LangSmith가 모른다 — 기대값을 Dataset으로 올리고 `client.evaluate()`로 돌려야 점수가 남는다
- **채점은 내 컴퓨터에서 한다.** 평가 파일이 `graph`를 import해 바깥에서 실행하고, 결과 State를 읽어 내 평가 함수로 채점한 뒤 점수만 LangSmith에 올린다. 그래프 안에 평가 코드는 없다
- LangSmith에 올리는 이유: 실패한 사례를 누르면 **그때의 Trace**(Gemini에 보낸 프롬프트와 답)가 바로 열리고, 실험끼리 나란히 비교할 수 있다
- 강의의 LLM-as-judge(LLM이 답변을 채점)와 Tool 호출 비교는 우리에게 거의 필요 없다. 답변은 정해진 틀이라 문자열 비교로 충분하고, 흐름은 엣지가 보장한다. **흔들릴 수 있는 곳은 `understand` 하나**라서 "말을 제대로 알아들었나"만 재면 된다

**실험 1 — `understand` 채점 (사례 3개, Gemini 3회)**

| 사례 | 질문 | 기대 (`intent` / `params` / 멈춘 곳) | 결과 |
|---|---|---|---|
| `balance` | 생활비 잔액 얼마야? | 잔액 조회 / `accounts: [생활비]` / 멈추지 않음 | 통과 |
| `transfer` | 생활비에서 저축으로 10만 원 보내줘 | 즉시이체 / 생활비→저축, 100000 / `confirm_change` | 통과 |
| `missing_amount` | 생활비에서 저축으로 돈 보내줘 | 즉시이체 / 금액 없음 / `ask_more` | 통과 |

- 멈춘 곳은 `app.get_state(config).next`로 읽었다. `interrupt()`는 노드가 `return`하기 전에 멈추므로 `.next`에는 **멈춘 노드 자신**이 들어 있다(재개하면 그 노드를 처음부터 다시 실행)

**실험 2 — B25 사례 5번 반복 (Gemini 5회)**

"저축으로 10만 원 옮겨줘"(출금 계좌를 말하지 않음). 9월 29일에는 2번 중 1번 LLM이 출금 계좌를 지어냈다. 안전장치가 두 겹이라 따로 쟀다.

| 채점 항목 | 무엇을 | 어떻게 | 결과 |
|---|---|---|---|
| `llm_no_guess` | LLM 자체가 지어내지 않았나 | 코드가 짐작한 계좌를 지울 때 남기는 로그를 잡음 | 5/5 |
| `system_safe` | 최종적으로 출금 계좌가 비고 `ask_more`에서 멈췄나 | `params` + `get_state().next` | 5/5 |

- `client.evaluate(..., num_repetitions=5)`로 사례 하나를 5번 돌렸다
- 로그를 잡는 장치가 동작하는지는 가짜 로그로 따로 확인했다 (고장 나서 "안 지어냄"이 나온 게 아님)
- 오늘은 0/5로 지어내지 않았지만 5번은 적어서 "이제 안 지어낸다"고 결론 내리지 않는다. 중요한 건 `system_safe`가 LLM과 **상관없이** 항상 통과해야 한다는 것 — B25를 프롬프트가 아니라 코드로 막은 이유가 점수에 그대로 드러났다
- 처음 실행은 LangSmith 인증 오류로 실패했다. `Client()`를 `.env`를 읽기(`load_env()`) 전에 만들었기 때문. 평소 Tracing은 그래프가 LLM을 만들기 전에 `load_env()`를 부르므로 영향 없음

## 배운 것

- 공개하고 나서야 보이는 실패가 있다. 혼자 쓸 때는 503을 거의 못 봤다.
- 라이브러리 기본값을 확인하자. "알아서 재시도"가 친절해 보여도 사용자는 그동안 멈춘 화면을 본다.
- "워크플로우 vs 에이전트": 흐름을 코드가 정하면 워크플로우, LLM이 정하면 에이전트. 돈이 오가는 승인 절차는 뒤에서 막는 것보다 **엣지로 길 자체를 없애는** 편이 확실하다.
- LLM에게 맡긴 판단이 많을수록 평가할 것도 많아진다. LLM을 한 곳으로 줄인 설계 덕분에 평가도 `understand` 하나로 끝난다. 한 번 돌리는 확인으로는 "몇 번 중 몇 번"을 알 수 없어서, LLM의 흔들림은 **반복 실험**으로 잰다.
