## 흐름

```
START → Intent & Parameter Parser (의도 분석 및 파라미터 추출)
  ├ Missing Info     → Ask for Missing Information → (User Response) → Parser로 되돌아감
  ├ Read-Only Query  → Process Account/Balance Query → END
  └ Complete Info    → Account & Balance Validator
                        ├ Insufficient Balance / Invalid Account → Handle Failure & Send Notice → END
                        └ Validation Passed → Request User Approval (Interrupt)
                                               ├ Approved           → Execute Transfer & Update JSON → END
                                               ├ Rejected/Cancelled → Handle Cancellation & Send Notice → END
                                               └ Modify Request     → Update Request Parameters → Validator로 되돌아감
```

| 분기 | 어디서 | 갈래 |
|---|---|---|
| Branch 1 | `Intent & Parameter Parser` 다음 | 정보 부족 / 단순 조회 / 정보 완비 |
| Branch 2 | `Account & Balance Validator` 다음 | 검증 통과 / 잔액 부족·계좌 오류 |
| Branch 3 | `Request User Approval` 다음 | 승인 / 거절·취소 / 조건 수정 |

**루프 2개**
- 정보가 부족하면 되묻고, 답을 받아 다시 해석한다.
- 승인 단계에서 조건을 고치면 파라미터를 수정하고 다시 검증한다.

## 초안의 구성 근거

| 초안의 부분 | 대응하는 명세 요구사항 | 그래서 이렇게 그렸다 |
|---|---|---|
| `Intent & Parameter Parser`를 맨 앞에 | 모든 요청 예시가 자연어 ("생활비에서 저축으로 10만 원 옮겨줘") | 무엇을 하든 먼저 말을 의도와 값으로 바꿔야 다음 단계가 판단할 수 있다 |
| Branch 1을 정보 부족 / 조회 / 정보 완비 3갈래로 | 명세 ①~③의 기능이 **조회**(계좌·거래 내역·카드)와 **변경**(이체·잠금·납부) 두 종류 + ④ "정보 부족 안내 / 추가 질문" | 해석 직후 "값이 다 있나", "바꾸는 업무인가"로 나누면 모든 기능이 세 길 중 하나로 들어간다 |
| `Ask for Missing Information` → Parser로 되돌아감 | ④ "필수 파라미터 미비 시 역질문하여 대화 이어나가기" | 답을 받으면 다시 해석해야 값이 채워지므로 Parser로 돌아가는 루프 |
| 조회는 승인 없이 바로 `END` | ④ 승인은 "데이터 변경 발생 시" | 아무것도 바꾸지 않는 조회에는 승인 단계가 필요 없다 |
| 승인 **전에** `Account & Balance Validator` | ① 즉시이체 "확인하고 승인 후 이체", 이체 한도 초과 시 거절 안내 | 실행할 수 없는 요청에 승인을 받으면 의미가 없으므로, 먼저 걸러내고 실패는 바로 안내 |
| `Request User Approval - Interrupt` | ④ "사용자에게 최종 확답 요청 (`interrupt` 처리)" | 명세가 방식까지 정해 둔 부분이라 그대로 노드로 |
| Branch 3을 승인 / 거절·취소 / 조건 수정 3갈래로 | ④ "자연어 승인/취소", "승인 전 수정" | 승인 단계에서 나올 수 있는 답이 이 세 가지 |
| 조건 수정 → Validator로 되돌아감 | ④ "조건 수정 시 반영 후 재검토" | 바뀐 값도 다시 검증을 거쳐야 하므로 Parser가 아니라 Validator로 |
| `Execute Transfer & Update JSON` | 데이터가 JSON 파일로 주어짐 | 실행과 저장을 한 단계로 |
| 노드 이름이 이체 중심 | 명세 ①에 이체 기능이 가장 많고, 승인 흐름의 대표 예시가 이체 | 가장 대표적인 업무 하나로 흐름을 먼저 잡았다 |

**초안에 담지 못한 명세 요구사항**: ④ "대화 맥락 및 후속 조회"(처리 결과 기록)와 "재시작 및 장애 복구"(체크포인터)는 초안에 대응하는 부분이 없다. 이 두 가지는 아래 "부족한 점"과 v1 설계에서 다뤘다.

## 검토

**잘된 점**
- 해석(`Parser`)을 맨 앞 한 곳에 둬서, 자연어를 구조화된 값으로 바꾸는 일이 흩어지지 않는다.
- 데이터를 바꾸기 전에 승인 단계(`Interrupt`)를 둬서 과제의 핵심을 짚었다.
- 조건 수정 → 재검증 루프가 닫혀 있어서, 고친 값도 다시 검증을 거친다.
- 모든 경로가 `END` 하나로 끝난다.

**부족한 점** (v1에서 보완)
- 노드 이름에 업무명(`Transfer`)이 들어가 있어서, 카드 잠금 같은 업무를 추가하면 그래프를 또 그려야 한다.
- 실패·취소 노드가 각자 안내 문장을 만들어서, 응답 말투가 경로마다 달라질 수 있다.
- 사용자 답변을 받는 부분이 화살표(`User Response`)로만 있어서, 어디서 멈추고 어떻게 이어 가는지가 없다.
- 저장에 실패했을 때의 경로가 없다.
- 처리 결과(성공·실패·취소)를 기록하는 곳이 없어서, "아까 이체 됐어?" 같은 후속 조회에 답할 근거가 없다.
- 승인 직전에만 검증해서, 승인을 기다리는 사이 잔액이 바뀌면 잡지 못한다.
