# 코드읽기가이드 — 처음부터 코드를 파악하기 위한 학습용 인수인계서

| 항목 | 내용 |
|---|---|
| 목적 | 이 문서만 따라 읽으면 **코드를 설명할 수 있게** 되는 것 (명세: "각자 설계의 변경 이유와 최종 흐름·분기 조건을 설명할 수 있어야 한다") |
| 쓰는 방식 | Step이 끝날 때마다 해당 파일을 추가한다 |
| 다루는 범위 | 현재 Step 0~3 (`intents`, `integrity`, `data_store`, `functions`, `config`, `graph`) |
| 왜 그렇게 설계했나 | 여기서는 짧게만. 자세한 이유는 [설계서.md](설계서.md), [설계변경기록.md](설계변경기록.md) |

> 각 파일은 같은 틀로 쓴다: **한 줄 요약 → 먼저 읽을 것 → 읽는 순서 → 핵심 코드 → 쓰인 개념 → 직접 해보기 → 스스로 확인.**
> "스스로 확인" 질문에 막히면 그 부분을 다시 읽는다. 이 질문들이 그대로 **평가·면접 예상 질문**이다.
> "쓰인 개념"의 번호는 00~29 개념정리 번호다 (TIL `2026-09-21 (2)시험 정리_langchain_개념정리_00-29`).

## 0. 전체 그림 먼저

### 읽는 순서 — 의존성이 없는 것부터

```
intents.py → integrity.py → data_store.py → functions.py → config.py → graph.py → (main.py, Step 4)
 (약속)       (장부 규칙)     (저장 통로)      (업무)          (설정)      (흐름)      (입구)
```

뒤의 파일은 앞의 파일을 불러다 쓴다. 앞에서부터 읽으면 "이게 어디서 왔지?"가 생기지 않는다.

### 질문 하나가 흐르는 길 (Step 3 기준)

```
"생활비 잔액 얼마야?"
  → graph.understand     내 계좌 이름 목록으로 Pydantic 모델을 만들고 Gemini 1회 호출
                          → intent="account_list_with_balance", params={"accounts": ["생활비"]}
  → graph.route_request  조회냐? → read_task
  → graph.read_task      functions.READ_TASKS에서 조회 함수를 찾아 실행 (data_store.load로 읽기만)
  → graph.respond        READ_TASKS에서 문장 틀을 찾아 → "생활비 계좌 잔액은 520,000원입니다."
```

### 한 번에 확인하기

```bash
uv run python src/integrity.py    # 결과: 8/8 통과
uv run python src/data_store.py   # 결과: 8/8 통과   (작업용 복사본을 지우고 다시 만듦)
uv run python src/functions.py    # 결과: 12/12 통과
uv run python src/config.py       # 키 설정 여부 True/False
uv run python src/graph.py        # 결과: 8/8 통과   (Gemini 7회 호출 — 비용 발생)
```

## 1. `intents.py` — 업무 이름표의 유일한 정의처

**한 줄 요약**: 에이전트가 할 수 있는 업무(intent)와 각 업무에 필요한 값(slot)을 **한 곳에** 적어둔 표.

**먼저 읽을 것**: 없음 (가장 바닥).

**읽는 순서**: 맨 위 설명(docstring) → `INTENTS` 표 → `READ_INTENTS`/`WRITE_INTENTS` → 특별한 값 3개.

**핵심 코드**

| 무엇 | 볼 것 |
|---|---|
| `INTENTS` | intent마다 `label`(짧은 이름), `desc`(설명), `kind`(read/write), `required`, `optional` |
| `READ_INTENTS`, `WRITE_INTENTS` | 표에서 **자동으로** 뽑아낸 집합. 손으로 따로 적지 않는 이유 |
| `UNSUPPORTED`, `NOT_UNDERSTOOD`, `UNCERTAIN` | 표 밖의 특별한 값. 누가 넣는지(LLM/코드)가 다름 |

**쓰인 개념**: 04 Structured Output(허용값 제한의 재료), 15 Router(분류할 목록)

**스스로 확인**
- 이름이 왜 `lock_card`가 아니라 `card_lock_temporary`인가? (`대상_동작_세부` 규칙과 정렬)
- "계좌 목록"과 "생활비 잔액"은 왜 같은 intent인가? (처리가 같으면 slot으로 구분)
- `required`와 `optional`의 차이가 그래프에서 어떤 차이를 만드나? (되묻기 여부)
- intent 이름을 `intents.py`에만 두는 이유는? (여러 파일이 주고받는 약속 — 어긋나면 `KeyError`)

## 2. `integrity.py` — 장부가 말이 되는지 검사

**한 줄 요약**: JSON 데이터가 은행 장부로서 맞는지 **8개 규칙**으로 검사한다. 저장할 때마다 불린다.

**먼저 읽을 것**: `data/initial_data.json`을 한 번 열어서 모양을 본다.

**읽는 순서**: `RULES` 표 → `check_integrity()` 안을 규칙 번호 순서로 → `main()`.

**핵심 코드**

| 무엇 | 볼 것 |
|---|---|
| `check_integrity()`의 `running` | 계좌마다 **0원에서 시작해** 거래를 시간순으로 더하고 뺀다 → 마지막에 저장된 잔액과 비교 (규칙 1·2) |
| 규칙 8 (`NAME_FIELDS`) | 같은 소유자 안에서 계좌·카드 이름이 겹치지 않는지. **이름 → ID가 1:1**이어야 하는 이유 |
| `main()`의 `sys.exit(1)` | 실패하면 종료 코드 1 — 다른 도구가 실패를 알 수 있게 |

**쓰인 개념**: (LangChain 개념은 없음) 데이터 무결성, 대사(reconciliation)

**직접 해보기**: `data/initial_data.json`의 잔액 하나를 1원 바꿔 저장하고 `uv run python src/integrity.py` → 규칙 1에서 실패하는 걸 본 뒤 **원래대로 되돌린다.**

**스스로 확인**
- 왜 "모든 계좌는 0원에서 시작"으로 가정했나? (실제 계좌 개설)
- "이체는 출금·입금이 짝을 이룬다" 규칙은 왜 없나? (지금 거래 구조로는 외부 출금과 구분 불가)
- 검사기를 만들고 **먼저 실패하는 걸 본** 이유는? (red first — 무조건 통과만 하는 검사기를 걸러내려고)

## 3. `data_store.py` — 파일로 가는 유일한 문

**한 줄 요약**: JSON을 읽고 쓰는 유일한 통로. 저장 전에 검사하고, 쓰다가 죽어도 파일이 깨지지 않게 저장한다.

**먼저 읽을 것**: `integrity.py` (`save()`가 부름).

**읽는 순서**: 경로 상수 → 에러 클래스 3개 → `save()` → `load()`·`ensure_working_copy()` → `reset()` → `_self_check()`.

**핵심 코드**

| 무엇 | 볼 것 |
|---|---|
| `DataStoreError` > `IntegrityError` / `StorageError` | 에러를 **"다시 하면 되느냐"** 로 나눈 계층 |
| `save()`의 순서 | [0] 무결성 검사 → [1] 임시 파일에 쓰고 `fsync` → [2] `os.replace`로 교체 |
| `_read_json()`의 `raise ... from e` | 파이썬 기본 에러를 우리 에러로 바꾸면서 원인을 함께 남김 |
| `load()` 첫 줄 | 복사본이 없으면 그 자리에서 만든다 (lazy initialization) |

**쓰인 개념**: 27 Fault Tolerance(재시도할 에러만 고르기 — `retry_on`), 29 Logging(`logger.info`)

**직접 해보기**: `uv run python src/data_store.py` → 8/8. "잔액만 1원 바꿔서 저장" 확인 항목이 무엇을 흉내 낸 건지 생각해본다.

**스스로 확인**
- 왜 파일에 바로 쓰지 않고 임시 파일을 거치나? (atomic write — 반쪽 파일 방지)
- 원본(`initial_data.json`)과 복사본(`bank_data.json`)을 왜 나눴나? 백업과 무엇이 다른가? (seed data — 원본은 갱신되지 않는 시작점)
- `IntegrityError`와 `StorageError`를 왜 나눴나? (재시도해서 될 것 / 안 될 것)
- Windows에서 `StorageError`가 나는 흔한 이유는? (`bank_data.json`을 편집기로 열어둔 채 저장)

## 4. `functions.py` — 업무별 코드 (지금은 조회)

**한 줄 요약**: "무슨 업무인지"를 아는 유일한 파일. 조회 함수, 문장 틀, 그리고 그래프가 찾아 쓰는 **업무 표**(`READ_TASKS`)가 있다.

**먼저 읽을 것**: `intents.py`, `data_store.py`.

**읽는 순서**: `CURRENT_USER_ID` → `_my_accounts()`·`_my_cards()` → `my_account_names()` → `account_list_with_balance()` → `format_account_list_with_balance()` → `READ_TASKS`.

**핵심 코드**

| 무엇 | 볼 것 |
|---|---|
| `_my_accounts()` | **인가** — 내 계좌만 남김. user_02의 "생활비"는 여기서 빠진다 |
| `account_list_with_balance()` | 검색하지 않고 **걸러내기만**. 내 계좌에 없는 이름이면 `ValueError` (버그로 드러냄) |
| 새 dict로 돌려주기 | 내부 정보(`owner_id`)가 빠지고, 받는 쪽이 고쳐도 원래 데이터는 안 바뀜 |
| `format_...()` | 숫자는 코드가 그대로 옮김 → 자릿수가 틀릴 일이 없음 |
| `READ_TASKS` | intent → {실행 함수, 문장 틀}. 조회 업무를 추가하면 **여기에 한 줄** |
| `save`를 import하지 않음 | 조회가 데이터를 바꿀 방법 자체가 없음 |

**쓰인 개념**: (Strategy 패턴·registry), 16 Guardrails와 같은 발상(애초에 못 하게 만들기)

**스스로 확인**
- 없는 이름이 들어오면 왜 조용히 빼지 않고 에러를 내나? (앞 단계의 약속 위반 = 버그 / 설계 원칙 6)
- 잔액을 왜 `"520,000원"`이 아니라 `520000`으로 돌려주나? (함수는 데이터, `respond`는 문장)
- `account_id`는 사용자에게 안 보여주는데 왜 돌려주나? (후속 대화 "그 계좌에서"용)

## 6. `graph.py` — 그래프 (Step 3: 조회 경로)

**한 줄 요약**: State, 노드, 조건부 Edge를 정의하고 조립한다. **LLM을 부르는 곳은 `understand` 하나뿐.**

**먼저 읽을 것**: 위의 다섯 파일 전부.

**읽는 순서**: `AgentState` → `build_graph()`(전체 모양부터) → `understand` → `route_request` → `read_task` → `respond` → `_self_check()`.

**핵심 코드**

| 무엇 | 볼 것 |
|---|---|
| `AgentState` | `messages`는 대화 내내(`add_messages`), 나머지는 **한 턴짜리** |
| `build_graph()` | 네모(`add_node`) / 마름모(`add_conditional_edges`) / `START`·`END`(표식). 시작할 때 `READ_TASKS`와 `READ_INTENTS`가 맞는지 확인 |
| `_build_schema()` | 계좌·카드 이름으로 `Literal`을 **실행할 때마다** 만든다 (`create_model`). 각 칸의 `description`이 LLM에게 가는 지시문 |
| `understand`의 `try` | **LLM 호출 한 줄만** 감쌈. API 키 확인은 일부러 `try` 밖 |
| `understand`의 반환 | 한 턴짜리 칸을 **통째로 새로 씀** + `result`를 비움 → 이전 질문 값이 안 남음 |
| `_find_inferred()` | LLM이 고른 이름이 사용자 말에 글자로 없으면 = 뜻으로 추측 → `respond`가 "'여행 자금' 계좌로 이해했어요." |
| `route_request` | 노드가 아니라 방향만 정하는 함수 (State를 안 바꿈) |
| `respond` | 모든 경로가 모이는 곳. 정해진 틀로 문장 생성 (LLM 안 씀) |

**쓰인 개념**: 04 Structured Output, 11 State·Node·조건부 Edge·Reducer, 13 Checkpointer(`InMemorySaver`, `thread_id`), 15 Router(`unsupported` = 15번의 `uncertain`), 29 Logging(`reason`은 State가 아니라 로그로)

**직접 해보기**: `uv run python src/graph.py` (Gemini 7회). LangSmith의 `langgraph-financial-agent` 프로젝트에서 `understand`가 무엇을 골랐는지 본다.

**스스로 확인**
- 네모와 마름모는 코드에서 어떻게 다르게 등록되나?
- 질문 한 번에 LLM은 몇 번 불리나? 왜 그렇게 설계했나? (1회 — 입구에만 LLM)
- `understand`가 `params`를 이전 값과 합치지 않고 새로 쓰는 이유는? (Checkpointer가 이전 턴을 들고 있음)
- "휴가비 계좌"를 LLM이 여행 자금으로 고른 원인은 무엇이었고 어떻게 확인했나? (통제 실험 — 새 대화에서도 같음 → 뜻으로 추측하는 경향)
- 왜 그 추측을 막지 않고 **알려주기로** 했나?
- 확인 코드는 왜 "이어 묻기"만 한 대화로 묻고 나머지는 질문마다 새 대화로 묻나?
