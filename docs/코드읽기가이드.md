# 코드읽기가이드 — 처음부터 코드를 파악하기 위한 학습용 인수인계서

| 항목 | 내용 |
|---|---|
| 목적 | 이 문서만 따라 읽으면 **코드를 설명할 수 있게** 되는 것 (명세: "각자 설계의 변경 이유와 최종 흐름·분기 조건을 설명할 수 있어야 한다") |
| 쓰는 방식 | Step이 끝날 때마다 해당 파일을 추가한다 |
| 다루는 범위 | 현재 Step 0~9 (`intents`, `integrity`, `data_store`, `functions`, `config`, `graph`, `main`, `scenarios`, `evaluation`) |
| 왜 그렇게 설계했나 | 여기서는 짧게만. 자세한 이유는 [설계서.md](설계서.md), [설계변경기록.md](설계변경기록.md) |

> 각 파일은 같은 틀로 쓴다: **한 줄 요약 → 먼저 읽을 것 → 읽는 순서 → 핵심 코드 → 쓰인 개념 → 직접 해보기 → 스스로 확인.**
> "스스로 확인" 질문에 막히면 그 부분을 다시 읽는다. 이 질문들이 그대로 **평가·면접 예상 질문**이다.
> "쓰인 개념"의 번호는 00~29 개념정리 번호다 (TIL `2026-09-21 (2)시험 정리_langchain_개념정리_00-29`).

## 0. 전체 그림 먼저

### 읽는 순서 — 의존성이 없는 것부터

```
intents.py → integrity.py → data_store.py → functions.py → config.py → graph.py → main.py
 (약속)       (장부 규칙)     (저장 통로)      (업무)          (설정)      (흐름)      (입구)
```

뒤의 파일은 앞의 파일을 불러다 쓴다. 앞에서부터 읽으면 "이게 어디서 왔지?"가 생기지 않는다.

### 질문 하나가 흐르는 길 (Step 4 기준)

```
"생활비 잔액 얼마야?"
  → main.run_turn        입력 한 줄을 HumanMessage로 감싸 graph.invoke (같은 thread_id = 같은 대화)
  → graph.understand     내 계좌 이름 목록으로 Pydantic 모델을 만들고, 지금 말 + <이전 상태>로 Gemini 1회 호출
                          → intent="account_list_with_balance", params={"accounts": ["생활비"]}
  → graph.route_request  조회냐? → read_task
  → graph.read_task      functions.READ_TASKS에서 조회 함수를 찾아 실행 (data_store.load로 읽기만)
  → graph.respond        READ_TASKS에서 문장 틀을 찾아 → "생활비 계좌 잔액은 520,000원입니다."
```

### 한 번에 확인하기

```bash
uv run python src/integrity.py    # 결과: 10/10 통과
uv run python src/data_store.py   # 결과: 10/10 통과   (작업용 복사본을 지우고 다시 만듦)
uv run python src/functions.py    # 결과: 31/31 통과
uv run python src/config.py       # 키 설정 여부 True/False
uv run python src/graph.py        # 그래프 모양을 Mermaid로 출력 (API 없음)
uv run python src/scenarios.py    # 대화 시나리오 47개 (Gemini 41회 호출 — 비용 발생)
uv run python src/evaluation.py --offline   # 채점 함수 8/8 (API 없음). 옵션 없이 실행하면 LangSmith Experiment (Gemini 4회)
uv run python src/main.py         # 대화해 보기 ('종료'로 끝냄, 질문마다 Gemini 1회)
```

## 1. `intents.py` — 업무 이름표의 유일한 정의처

**한 줄 요약**: 에이전트가 할 수 있는 업무(intent)와 각 업무에 필요한 값(slot)을 **한 곳에** 적어둔 표.

**먼저 읽을 것**: 없음 (가장 바닥).

**읽는 순서**: 맨 위 설명(docstring) → `INTENTS` 표 → `READ_INTENTS`/`WRITE_INTENTS` → 특별한 값 3개.

**핵심 코드**

| 무엇 | 볼 것 |
|---|---|
| `INTENTS` | intent마다 `label`(짧은 이름), `desc`(설명), `kind`(read/write), `required`, `optional` |
| `READ_INTENTS`, `WRITE_INTENTS` | 표에서 **자동으로** 뽑아낸 집합. 손으로 따로 적지 않는 이유 |
| `UNSUPPORTED`, `NOT_UNDERSTOOD`, `UNCERTAIN` | 표 밖의 특별한 값. 누가 넣는지(LLM/코드)가 다름 |
| `SLOTS` | 칸마다 `kind`(계좌·카드)·`role`("출금 계좌")·`suffix`. 그래프가 칸의 종류를 몰라도 되게 (Step 7) |
| `NAME_SLOTS`, `KIND_LABELS` | `SLOTS`에서 자동으로 뽑은 이름 칸 목록 / 종류의 이름 |

**쓰인 개념**: 04 Structured Output(허용값 제한의 재료), 15 Router(분류할 목록)

**스스로 확인**
- 이름이 왜 `lock_card`가 아니라 `card_lock_temporary`인가? (`대상_동작_세부` 규칙과 정렬)
- "계좌 목록"과 "생활비 잔액"은 왜 같은 intent인가? (처리가 같으면 slot으로 구분)
- `required`와 `optional`의 차이가 그래프에서 어떤 차이를 만드나? (되묻기 여부)
- intent 이름을 `intents.py`에만 두는 이유는? (여러 파일이 주고받는 약속 — 어긋나면 `KeyError`)
- 카드 잠금을 추가할 때 `graph.py`를 고쳐야 했던 이유는? (slot의 종류 정보가 `graph.py`에 있었음 → `SLOTS`로 옮김)

## 2. `integrity.py` — 장부가 말이 되는지 검사

**한 줄 요약**: JSON 데이터가 은행 장부로서 맞는지 **10개 규칙**으로 검사한다. 저장할 때마다 불린다.

**먼저 읽을 것**: `data/initial_data.json`을 한 번 열어서 모양을 본다.

**읽는 순서**: `RULES` 표 → `check_integrity()` 안을 규칙 번호 순서로 → `main()`.

**핵심 코드**

| 무엇 | 볼 것 |
|---|---|
| `check_integrity()`의 `running` | 계좌마다 **0원에서 시작해** 거래를 시간순으로 더하고 뺀다 → 마지막에 저장된 잔액과 비교 (규칙 1·2) |
| 규칙 8 (`NAME_FIELDS`) | 같은 소유자 안에서 계좌·카드 이름이 겹치지 않는지. **이름 → ID가 1:1**이어야 하는 이유 |
| 규칙 9 (`transfer_pairs`) | 같은 `transfer_id`로 묶인 거래가 출금 1 + 입금 1인지. 이체 코드가 입금 줄을 빠뜨리면 잔액을 맞춰도 여기서 걸린다 (Step 5) |
| 규칙 10 (`transfer_recorded`) | 모든 이체에 완료 기록이 있고 그 반대도 성립하는지. 거래와 기록을 같은 저장으로 남긴다는 약속을 검사 (Step 6) |
| `main()`의 `sys.exit(1)` | 실패하면 종료 코드 1 — 다른 도구가 실패를 알 수 있게 |

**쓰인 개념**: (LangChain 개념은 없음) 데이터 무결성, 대사(reconciliation)

**직접 해보기**: `data/initial_data.json`의 잔액 하나를 1원 바꿔 저장하고 `uv run python src/integrity.py` → 규칙 1에서 실패하는 걸 본 뒤 **원래대로 되돌린다.**

**스스로 확인**
- 왜 "모든 계좌는 0원에서 시작"으로 가정했나? (실제 계좌 개설)
- "이체는 출금·입금이 짝을 이룬다" 규칙은 처음에 왜 없었고, 지금은 어떻게 검사하나? (외부 출금과 구분 불가 → `transfer_id`로 묶음)
- 검사기를 만들고 **먼저 실패하는 걸 본** 이유는? (red first — 무조건 통과만 하는 검사기를 걸러내려고)

## 3. `data_store.py` — 파일로 가는 유일한 문

**한 줄 요약**: JSON을 읽고 쓰는 유일한 통로. 저장 전에 검사하고, 쓰다가 죽어도 파일이 깨지지 않게 저장한다.

**먼저 읽을 것**: `integrity.py` (`save()`가 부름).

**읽는 순서**: 경로 상수 → 에러 클래스 3개 → `save()` → `load()`·`ensure_working_copy()` → `reset()` → `_self_check()`.

**핵심 코드**

| 무엇 | 볼 것 |
|---|---|
| `DataStoreError` > `IntegrityError` / `StorageError` | 에러를 **"다시 하면 되느냐"** 로 나눈 계층 |
| `save()`의 순서 | [0] 무결성 검사 → [1] 임시 파일에 쓰고 `fsync` → [2] `os.replace`로 교체 |
| `save()`의 재시도 루프 | [1]·[2]가 실패하면 `SAVE_ATTEMPTS`(3)번까지. 교체 전까지 진짜 파일은 그대로라 안전 (Step 6) |
| `_read_json()`의 `raise ... from e` | 파이썬 기본 에러를 우리 에러로 바꾸면서 원인을 함께 남김 |
| `load()` 첫 줄 | 복사본이 없으면 그 자리에서 만든다 (lazy initialization) |

**쓰인 개념**: 27 Fault Tolerance(재시도할 에러만 고르기 — `retry_on`), 29 Logging(`logger.info`)

**직접 해보기**: `uv run python src/data_store.py` → 10/10. "잔액만 1원 바꿔서 저장" 확인 항목이 무엇을 흉내 낸 건지 생각해본다.

**스스로 확인**
- 왜 파일에 바로 쓰지 않고 임시 파일을 거치나? (atomic write — 반쪽 파일 방지)
- 원본(`initial_data.json`)과 복사본(`bank_data.json`)을 왜 나눴나? 백업과 무엇이 다른가? (seed data — 원본은 갱신되지 않는 시작점)
- `IntegrityError`와 `StorageError`를 왜 나눴나? (재시도해서 될 것 / 안 될 것)
- Windows에서 `StorageError`가 나는 흔한 이유는? (`bank_data.json`을 편집기로 열어둔 채 저장)
- 재시도를 LangGraph `RetryPolicy`가 아니라 여기서 하는 이유는? (원인을 아는 곳. 노드가 실패를 받아 기록하면 바깥 재시도는 실패를 못 봄)
- `rollback` 노드가 없는데 저장 실패 시 장부가 어떻게 유지되나? (복사본에서 바꾸고 한 번에 교체)

## 4. `functions.py` — 업무별 코드 (조회 + 이체 + 카드 잠금)

**한 줄 요약**: "무슨 업무인지"를 아는 유일한 파일. 조회 함수, 문장 틀, 변경 Handler, 그리고 그래프가 찾아 쓰는 **업무 표**(`READ_TASKS`, `HANDLERS`)가 있다.

**먼저 읽을 것**: `intents.py`, `data_store.py`.

**읽는 순서**: `CURRENT_USER_ID` → `_my_accounts()`·`_my_cards()` → `my_account_names()` → `account_list_with_balance()` → `format_account_list_with_balance()` → `READ_TASKS` → `TransferInstantHandler` (`validate` → `describe` → `apply`) → `HANDLERS`.

**핵심 코드**

| 무엇 | 볼 것 |
|---|---|
| `_my_accounts()` | **인가** — 내 계좌만 남김. user_02의 "생활비"는 여기서 빠진다 |
| `account_list_with_balance()` | 검색하지 않고 **걸러내기만**. 내 계좌에 없는 이름이면 `ValueError` (버그로 드러냄) |
| 새 dict로 돌려주기 | 내부 정보(`owner_id`)가 빠지고, 받는 쪽이 고쳐도 원래 데이터는 안 바뀜 |
| `format_...()` | 숫자는 코드가 그대로 옮김 → 자릿수가 틀릴 일이 없음 |
| `READ_TASKS` | intent → {실행 함수, 문장 틀}. 조회 업무를 추가하면 **여기에 한 줄** |
| `save`를 import하지 않음 | 조회가 데이터를 바꿀 방법 자체가 없음. **이체 Handler도 `data`만 바꾸고 저장은 그래프의 `apply_change`가** |
| `validate()` | 업무 검사만 (금액 > 0, 출금 ≠ 입금, 잔액). 거절은 에러가 아니라 **사유 문장**. 처리안 만들 때와 실행 직전에 같은 함수 |
| `describe()` | 승인 화면 문장 — 방향·금액·이체 후 잔액 |
| `apply()` | 잔액 두 곳 + 거래 두 줄(같은 `transfer_id`)을 함께 바꿈 |
| `HANDLERS` | intent → Handler. 변경 업무를 추가하면 **여기에 한 줄** |
| `CardLockTemporaryHandler` | 두 번째 변경 업무. `active`만 잠그고, 이미 잠김·분실 정지는 사유로 거절. `apply`는 `status`만 바꿈 |
| `NAME_LISTS` | 종류(`account`/`card`) → 이름 목록 함수. 되묻기·`uncertain` 후보 |
| `josa()` | 받침에 맞는 조사 ("저축으로", "생활비로") |
| `new_request()` | 처리 기록 한 건. 어느 업무든 같은 틀, `details`만 Handler의 `details()`가 채움 (ID로) |
| `apply()`의 반환 | `(완료 문장, {"transfer_id": ...})` — 두 번째 값이 완료 기록의 `details`에 들어감 |

**쓰인 개념**: (Strategy 패턴·registry), 16 Guardrails와 같은 발상(애초에 못 하게 만들기)

**스스로 확인**
- 없는 이름이 들어오면 왜 조용히 빼지 않고 에러를 내나? (앞 단계의 약속 위반 = 버그 / 설계 원칙 6)
- 잔액을 왜 `"520,000원"`이 아니라 `520000`으로 돌려주나? (함수는 데이터, `respond`는 문장)
- `account_id`는 사용자에게 안 보여주는데 왜 돌려주나? (후속 대화 "그 계좌에서"용)
- "필수 칸이 있나"는 Handler가 아니라 그래프가 검사한다. 왜? (어느 업무든 같은 형식 검사 — `intents.py` 기준)
- 실행 직전에 `validate`를 **다시** 부르는 이유는? (승인을 기다리는 사이 잔액이 바뀔 수 있음, TOCTOU)

## 6. `graph.py` — 그래프 (조회 · 이전 상태 · 승인 · 기록 · 되묻기 · 수정)

**한 줄 요약**: State, 노드, 조건부 Edge를 정의하고 조립한다. **LLM을 부르는 곳은 `understand` 하나뿐.**

**먼저 읽을 것**: 위의 다섯 파일 전부.

**읽는 순서**: `AgentState` → `build_graph()`(전체 모양부터) → `understand` → `_describe_previous`·`_carry_account` → `route_request` → `ask_more` → `read_task` → `plan_change` → `confirm_change` → `apply_change` → `respond` → `_self_check()`.

**핵심 코드**

| 무엇 | 볼 것 |
|---|---|
| `AgentState` | `messages`는 대화 내내(`add_messages`, 기록용). `intent`·`params`는 **턴을 넘어 이어짐**, `inferred`·`result`는 한 턴짜리 |
| `build_graph()` | 네모(`add_node`) / 마름모(`add_conditional_edges`) / `START`·`END`(표식). 시작할 때 `READ_TASKS`와 `READ_INTENTS`가 맞는지 확인 |
| `_build_schema()` | 계좌·카드 이름으로 `Literal`을 **실행할 때마다** 만든다 (`create_model`). 각 칸의 `description`이 LLM에게 가는 지시문 |
| `understand`의 `try` | **LLM 호출 한 줄만** 감쌈. API 키 확인은 일부러 `try` 밖 |
| `SYSTEM_PROMPT`의 `<이전 상태>`, 규칙 6~9 | 대화 기록 대신 직전 해석 결과를 준다. 유지·변경·추가·전체는 **LLM이** 뜻으로 판단 |
| `_describe_previous()` | 이번 턴 값을 쓰기 **전에** 직전 `intent`·`params`·후보를 한 줄로. 새 State 칸이 필요 없는 이유 |
| `_carry_account()` | 다른 업무로 넘길 계좌를 **코드가** 정함 — 하나일 때만. LLM이 개수를 잘못 센 뒤 옮김 |
| `understand`의 반환 | LLM이 낸 "이번 턴의 최종 값"으로 칸을 씀 + `result`를 비움 |
| `_find_inferred()` | LLM이 고른 이름이 사용자 말에 글자로 없고 **이전 상태에도 없으면** = 뜻으로 추측 → `respond`가 "'여행 자금' 계좌로 이해했어요." |
| `route_request` | 노드가 아니라 방향만 정하는 함수 (State를 안 바꿈). 조회 / `HANDLERS`에 있는 변경 / 그 외 |
| `understand`의 규칙 8 강제 | 다른 업무로 넘어가며 옮겨 온 계좌가 "이어받을 계좌"가 아니면 비움 — LLM이 프롬프트를 어긴 적이 있음 |
| `_form_problem()`, `_question()` | 필수 slot·`uncertain` 검사 → `missing`. 이름 칸이면 후보까지. 업무와 무관해서 그래프가 한다 |
| `_turn_reset()` | 새 요청이면 전부 비우고, 루프에서 돌아왔으면(`loop`) 처리안·횟수는 남긴다 |
| `ask_more` | 🛑 되묻기(루프 1). 답을 새 메시지로 붙여 `understand`로 — 병합 코드 없음. "취소"면 그만 |
| `understand`의 `loop == "revise"` | 수정 요청(루프 2). 바뀐 게 없으면 `unclear`, 다른 업무면 지금 요청 유지 |
| `plan_change` | 읽기만. 처리안 + 만든 시각 (승인 전에는 아무것도 바꾸지 않는다) |
| `confirm_change` | 🛑 `interrupt`. **재개되면 노드를 처음부터 다시 실행** → 앞에 부작용을 두지 않음. 답은 `_classify`(정해진 단어만), 5분 지났으면 `expired` |
| `route_decision` | 예/취소가 아닌 답(`revise`)은 `understand`로 (루프 2). 수정 5번 초과는 `too_many` |
| `plan_change`의 `revise_rejected` | 수정안이 걸리면 이전 처리안과 그 `params`로 되돌림 |
| `apply_change` | 새로 읽고 → 같은 `validate` → `apply` → **완료 기록 추가** → `save` (한 번에). 저장 실패(`DataStoreError`)는 받아서 안내 |
| `record_result` | 완료가 아닌 결과(취소·만료·실패)를 기록. 기록 저장이 실패해도 대화는 계속 |
| `_now()`, `_clock_offset` | 시계 주입. 테스트에서 6분 뒤를 흉내 낸다 |
| `respond` | 모든 경로가 모이는 곳. 정해진 틀로 문장 생성 (LLM 안 씀) |

**쓰인 개념**: 04 Structured Output, 11 State·Node·조건부 Edge·Reducer, 13 Checkpointer(`InMemorySaver`, `thread_id`), 15 Router(`unsupported` = 15번의 `uncertain`), 29 Logging(`reason`은 State가 아니라 로그로)

**직접 해보기**: `uv run python src/graph.py`로 흐름도를 보고, `uv run python src/scenarios.py`(Gemini 41회)로 대화를 돌려 본다. LangSmith의 `langgraph-financial-agent` 프로젝트에서 `understand`가 무엇을 골랐는지 본다.

**스스로 확인**
- 네모와 마름모는 코드에서 어떻게 다르게 등록되나?
- 질문 한 번에 LLM은 몇 번 불리나? 왜 그렇게 설계했나? (1회 — 입구에만 LLM)
- 대화 기록 대신 `<이전 상태>`를 넘기는 이유는? (Checkpointer가 직전 값을 이미 들고 있음 — 토큰, 옛 대화의 간섭)
- 이전 값과 합치는 일을 코드가 아니라 LLM이 하는 이유는? ("전부", "저축도", "저축은?"은 말의 뜻이라서)
- `accounts`가 빈 목록이면 왜 "전체"이고, "말하지 않음"과 어떻게 구분되나? (LLM이 유지할 값을 다시 적음)
- 이어받을 계좌의 개수는 왜 코드가 세나? (사실은 코드가 — LLM이 두 개를 "하나뿐"으로 셈)
- 코드가 "이어받을 계좌: 없음"을 알려줬는데도 왜 검증까지 하나? (LLM이 알려준 걸 어김 — 알려주기 ≠ 지키게 하기)
- 승인 답을 LLM으로 분류하지 않는 이유는? 부분 일치를 쓰지 않는 이유는?
- `confirm_change`에서 저장하면 안 되는 이유는? (재개 때 노드가 다시 실행됨)
- 검사 세 겹은 각각 무엇을 막나?
- 완료 기록을 `record_result`가 아니라 `apply_change`에서 남기는 이유는? (거래와 기록을 한 번의 저장으로)
- 잔액 부족은 왜 처리 기록이 없나? (승인 화면 전 — 고객이 그 자리에서 결과를 들음)
- 되묻기 후 `params`를 합치는 코드가 없는데 이전 값이 왜 안 날아가나? (`understand`가 이전 상태를 보고 최종 값을 냄)
- 수정안이 걸렸을 때 `params`도 되돌리는 이유는? (안 되돌리면 "예"에서 걸린 값으로 실행 시도)
- "음"이라고 답해도 승인 유효 시간이 늘지 않는 이유는? (바뀐 게 없으면 만든 시각을 이어감)
- "휴가비 계좌"를 LLM이 여행 자금으로 고른 원인은 무엇이었고 어떻게 확인했나? (통제 실험 — 새 대화에서도 같음 → 뜻으로 추측하는 경향)
- 왜 그 추측을 막지 않고 **알려주기로** 했나?
- 확인 코드는 왜 "이어 묻기"만 한 대화로 묻고 나머지는 질문마다 새 대화로 묻나?

## 9. `evaluation.py` — LLM 평가 (LangSmith Experiment)

**한 줄 요약**: LLM을 쓰는 `understand`가 말을 제대로 알아들었는지 Golden set으로 채점하고, 점수를 LangSmith Experiment로 남긴다. 같은 사례를 여러 번 돌려 "몇 번 중 몇 번"을 잰다.

**먼저 읽을 것**: `scenarios.py`(`ask`, `ScriptedLLM`), `graph.py`의 `understand` 끝부분(짐작한 출금 계좌를 비우는 곳), `data_store.use_ledger`.

**읽는 순서**: `GOLDEN_SET` → `target` → 채점 함수 4개 → `run_experiment` → `_self_check_offline`.

**핵심 코드**

| 무엇 | 볼 것 |
|---|---|
| `GOLDEN_SET` | 질문(`inputs`)과 기대값(`reference`: `intent`·`params`·`stopped_at`). 정상 조회·정상 이체·금액 누락·출금 계좌 누락(B25) |
| `target` | 그래프를 평소처럼 `invoke`하고 채점에 쓸 값만 돌려준다. 그래프 안에는 평가 코드가 없다 — 바깥에서 실행하고 결과만 읽는다 |
| `app.get_state(config).next` | 멈춘 노드. `interrupt()`는 노드가 `return`하기 전에 멈추므로 `.next`에 **멈춘 노드 자신**이 들어 있다. 끝까지 갔으면 `()` |
| `_GuessCatcher` | `understand`가 "짐작한 출금 계좌를 비움" 로그를 남겼는지 잡는다 → LLM 자체가 지어냈다는 증거 |
| `data_store.use_ledger` | 사례마다 원본에서 새 장부. 작업용 복사본을 건드리지 않고, 끝나면 지운다 |
| `_dataset_name` | Golden set 내용의 해시로 이름을 정한다 — 같으면 같은 Dataset(실험끼리 비교), 사례를 고치면 새 Dataset |
| `client.evaluate(..., num_repetitions=N)` | Dataset의 사례마다 `target` → 채점 함수 → 점수를 LangSmith에 올린다. 같은 사례를 N번 |

**쓰인 개념**: 평가의 네 요소 — Dataset(입력 + 기대값) · target(실행) · evaluator(채점) · Experiment(결과 기록). Tracing(자동으로 쌓이는 실행 기록)과 Evaluation(직접 기대값을 주고 채점)은 다르다.

**직접 해보기**
- `--offline`으로 채점 함수가 맞게 가르는지 본다 (가짜 LLM이 출금 계좌를 지어내면 `llm_no_guess`만 실패)
- `--repeat 5`로 실행한 뒤 LangSmith에서 실패한 칸을 눌러 그때의 Trace(Gemini에 보낸 프롬프트와 답)를 연다

**스스로 확인**
- 채점은 어디서 실행되나? LangSmith는 무엇을 하나? (이 컴퓨터 / 결과를 저장·비교해 보여줌)
- 왜 LLM-as-judge를 쓰지 않나? (답변이 정해진 틀이라 문자열 비교로 충분)
- `llm_no_guess`와 `params_correct`를 왜 따로 보나? (B25는 안전장치가 두 겹 — LLM이 뚫려도 코드가 막는지)
- 한 번 통과한 결과로 결론을 내리면 안 되는 이유는? (같은 질문에도 LLM 답이 흔들림)
