## A. 초안(FigJam) → v1 워크플로우

**날짜**: 2026-09-22 · **근거**: [devlog/2026-09-22 2~3절](../devlog/2026-09-22_워크플로우-설계-이해.md)

### 초안의 흐름

```
Start → Intent & Parameter Parser → Info Sufficiency Check
  ├ 정보 부족   → Clarification Question → Receive User Answer → (Parser로 되돌아감)
  ├ 단순 조회   → Query Processing → End: Query Result
  └ 정보 완비   → Account & Balance Validation → Transfer Validation Result
                   ├ 잔액 부족·계좌 오류 → Failure & Guidance → End: Transfer Failed
                   └ 검증 성공 → User Approval Request (Interrupt) → User Approval Response
                                  ├ 승인      → Transfer Execution & Save → End: Transfer Success
                                  ├ 거절·취소 → Cancellation Processing → End: Transfer Cancelled
                                  └ 조건 수정 → Parameter Modification → (Validation으로 되돌아감)
```

**초안에서 그대로 살린 것**: 해석 노드를 맨 앞에 두는 구조, 승인 지점에 `interrupt`, 조건 수정 → 재검증 루프, 정보 부족 → 되묻기 루프, 실패 경로를 따로 둔 것.

### 바뀐 것

| # | 처음 (초안) | 지금 (v1) | 왜 |
|---|---|---|---|
| A1 | `End`가 3개 (성공·실패·취소) + 조회 `End` | **`END` 1개**. 모든 경로가 `respond` → `END` | LangGraph의 `END`는 노드가 아니라 하나뿐인 표식. 결과 구분은 State가 담당. 응답 생성도 한 곳에 모아야 말투가 일관됨 |
| A2 | 노드 이름에 업무명 (`Transfer Validation`, `Transfer Execution & Save`) | 단계 이름 (`plan_change`, `apply_change`) | 업무명이 들어가면 카드·청구서를 얹을 때 그래프를 또 그려야 함. 업무 종류는 State의 `intent`가 담당 |
| A3 | `Receive User Answer`가 일반 노드 | `ask_more` 안의 `interrupt` | LangGraph에서 "답을 받는 것"은 노드가 아니라 **중단** 그 자체. 승인과 같은 방식으로 통일 |
| A4 | 되묻기 후 Parser로 돌아갈 때 규칙 없음 | 돌아갈 때 이전 값과 **병합** 명시 | 덮어쓰면 앞 턴에 알아낸 금액·계좌가 날아감 |
| A5 | 실행·저장 후 곧바로 성공 | `저장 성공?` 분기 + `rollback` | 명세: "검증이나 저장에 실패하면 이체 전 상태를 유지한다" |
| A6 | 처리 기록을 남기는 곳 없음 | `record_result` (성공·실패·취소 모두 기록) | 명세: "아까 이체가 됐어?" 같은 후속 조회의 근거 |
| A7 | 승인 전 검증 한 번 | 실행 직전(`apply_change`)에 **재검증** | 승인을 기다리는 사이 잔액이 바뀔 수 있음 (TOCTOU — 확인 시점과 사용 시점의 간극) |
| A8 | 검증과 실행이 업무별 노드에 섞임 | 업무별 차이는 `functions.py`의 표로, 노드는 절차만 | 기능이 20개여도 노드는 9개로 유지. 업무 추가 = 표에 한 줄 |

## B. 구현하면서 바뀐 설계

### B1. intent 이름

**날짜**: 2026-09-25 · **근거**: [devlog/2026-09-25 5절](../devlog/2026-09-25_문서검토-intent설계-데이터무결성.md)

| 처음 | 지금 |
|---|---|
| `list_accounts`, `transfer`, `lock_card` | `account_list_with_balance`, `transfer_instant`, `card_lock_temporary` |

**왜**: `transfer`는 즉시·조건부·분할 중 어느 이체인지, `lock_card`는 일시 잠금인지 분실 정지인지 이름으로 알 수 없었다. 규칙을 **`대상_동작_세부`** 로 정하면 알파벳순 정렬만으로 같은 업무끼리 모인다.

### B2. intent를 정의하는 곳

**날짜**: 2026-09-25 · **근거**: [devlog/2026-09-25 4절](../devlog/2026-09-25_문서검토-intent설계-데이터무결성.md)

| 처음 | 지금 |
|---|---|
| 정해진 곳 없음 (대화·문서마다 이름이 달랐음) | **`src/intents.py` 한 곳**. 프롬프트·스키마·분기·업무 표가 전부 여기서 가져감 |

**왜**: intent 이름은 여러 파일이 주고받는 약속(contract)이다. 한 글자라도 어긋나면 `KeyError`. 같은 정보를 여러 곳에 적으면 결국 어긋난다 (Single Source of Truth).

### B3. 초기 데이터 — 장부가 맞도록

**날짜**: 2026-09-25 · **근거**: [devlog/2026-09-25 8절](../devlog/2026-09-25_문서검토-intent설계-데이터무결성.md)

| 처음 | 지금 |
|---|---|
| 거래 20건. 거래를 다 더해도 잔액이 안 나옴 | 거래 30건. **모든 계좌 0원 시작** 기준으로 쌓으면 잔액과 정확히 일치 |
| 무결성 규칙 없음 | 규칙 7개 → 8개, 코드(`integrity.py`)로 검사 |

**왜**: 데이터가 처음부터 틀려 있으면, 이체 기능에 버그가 있는지 데이터가 원래 이상한지 구분할 수 없다. 0원 시작은 실제 계좌 개설과 같다.
처음 제안한 "이체는 출금·입금이 짝을 이룬다" 규칙은 **현재 거래 구조로는 검사할 수 없어** 빼고(→ C1), "미래 거래 없음"(09-25)과 "같은 사람의 이름 중복 금지"(09-26, → B5)를 넣었다.

### B4. 저장 — 틀린 장부는 파일에 못 들어간다

**날짜**: 2026-09-26 · **근거**: [devlog/2026-09-26 1·5절](../devlog/2026-09-26_Step1-data_store.md)

| 처음 (v1) | 지금 |
|---|---|
| `apply_change`가 JSON에 저장 (방식은 정하지 않음) | 저장은 `data_store.save()` 하나뿐. 저장 전 **무결성 검사**, 저장은 **atomic write** |

**왜**: 이체 코드가 거래 기록을 빠뜨리는 버그가 있어도 틀린 장부가 파일에 들어가지 못한다 ("저장하는 곳에서 막는다" — DB의 제약 조건과 같은 원리). 덕분에 `rollback` 경로가 실제로 테스트 가능한 경로가 됐다. 쓰다가 프로그램이 죽어도 반쯤 쓰인 파일이 남지 않는다.

### B5. 사용자가 말한 계좌를 찾는 방식 — 세 번 바뀜

**날짜**: 2026-09-26 · **근거**: [devlog/2026-09-26 9절](../devlog/2026-09-26_Step1-data_store.md)

| 안 | 방식 | 버린 이유 |
|---|---|---|
| 1안 | LLM은 사용자 말을 **그대로 옮기고**, 코드가 글자를 다듬어 검색 ("여행 계좌" → "여행 자금") | "여행 갈 때 쓰는 통장"처럼 **뜻으로 말한 표현**은 글자 검색으로 못 찾음. LLM은 목록만 주면 분류할 수 있음(15번 실습) |
| 2안 | 규칙으로 먼저 찾고, 정확히 겹치면 "맞나요?" 확인, 못 찾으면 LLM | 확실한 경우에도 묻는 건 **확인 피로**. 호출 절약도 거의 없었음(`understand`가 어차피 매번 LLM 1회) |
| **3안 (지금)** | LLM이 **역할 나누기 + 허용 목록(내 계좌 이름 + `uncertain`)에서 이름 고르기**를 한 번에. 코드는 **검증만** | — |

**왜 3안인가**: 한 문장에 계좌가 여러 개일 때 "~에서"·"~으로"로 역할을 나누는 건 LLM이 잘하고 규칙은 못 한다. 허용값을 강제하면 State에 이미 실제 이름이 들어오므로 검색할 것이 남지 않는다. 호출은 항상 1회.
**따라 들어간 것**: 이름 → ID가 1:1이어야 하므로 무결성 규칙 8(같은 사람의 계좌·카드 이름 중복 금지).

### B6. 조회 slot — 하나 → 목록

**날짜**: 2026-09-26 · **근거**: [devlog/2026-09-26 9절](../devlog/2026-09-26_Step1-data_store.md)

| 처음 | 지금 |
|---|---|
| `account` (이름 하나) | `accounts` (이름 목록) |

**왜**: "생활비랑 저축 잔액 보여줘"를 담을 자리가 없었다. "한 문장에 계좌 이름이 여러 개면?"이라는 질문에서 발견.

### B7. 검증을 두 층으로

**날짜**: 2026-09-26 · **근거**: [devlog/2026-09-26 9절](../devlog/2026-09-26_Step1-data_store.md)

| 처음 | 지금 |
|---|---|
| 검증을 어디서 할지 구분 없음 | **형식**(LLM이 약속을 지켰나)은 Pydantic 선언, **업무**(요청이 실행할 수 있는 내용인가 — 금액 > 0, 출금 ≠ 입금, 잔액)는 Handler |

**왜**: 사용자가 정말 "-1만 원"이라고 말했으면 LLM은 실수하지 않은 것이다. Pydantic이 막으면 LLM의 형식 실패처럼 보여서 "이체 금액은 0원보다 커야 합니다"라고 안내할 수 없다(명세 요구사항). **누구의 실수인지**에 따라 층을 나눴다.

### B8. 실패를 세 종류로

**날짜**: 2026-09-26 · **근거**: [devlog/2026-09-26 2절](../devlog/2026-09-26_Step1-data_store.md)

| 처음 | 지금 |
|---|---|
| 정하지 않음 | **업무상 거절**(에러 아님) / **저장 실패**(`DataStoreError` > `IntegrityError`·`StorageError`) / **버그**(받지 않음) |

**왜**: 잔액 부족 같은 평범한 거절까지 에러로 만들면 진짜 사고와 섞인다. 저장 실패를 두 개로 나눈 건 **재시도해서 될 것(파일 잠김)과 안 될 것(규칙 위반)** 을 가르기 위해서다.

### B9. State 칸 — 설계한 9개 중 쓰는 것만

**날짜**: 2026-09-26 · **근거**: [devlog/2026-09-26 12절](../devlog/2026-09-26_Step1-data_store.md)

| 처음 (v1) | 지금 |
|---|---|
| 9개 칸을 한 번에 설계 | 쓰는 칸만 도입 (Step 3: `messages`, `intent`, `params`, `inferred`, `result`). 나머지는 필요한 Step에서 |
| LLM의 판단 근거 `reason`도 State에 | `reason`은 **로그로** |

**왜**: "State에는 다른 노드가 읽는 것만 넣는다." `reason`은 어떤 노드도 읽지 않는다. 한 턴짜리 칸은 `understand`가 매번 새로 써서, Checkpointer가 들고 있는 이전 턴의 값이 섞이지 않게 했다.

### B10. 답변 문장 — 정해진 틀

**날짜**: 2026-09-26 · **근거**: [devlog/2026-09-26 12절](../devlog/2026-09-26_Step1-data_store.md)

| 처음 | 지금 |
|---|---|
| `respond`가 "결과를 문장으로" (방식은 정하지 않음) | **정해진 틀**. 업무별 틀은 `functions.py`의 `READ_TASKS`에 |

**왜**: 은행 앱에서 숫자는 틀리면 안 된다. LLM으로 쓰게 하면 묻지 않은 합계를 스스로 계산해 덧붙이기도 한다. 질문당 LLM 호출도 1회로 줄어든다. 음성 모드가 들어오면 "숫자는 틀, 말투만 LLM"을 다시 검토한다.

### B11. 뜻으로 추측한 이름은 해석을 밝힌다

**날짜**: 2026-09-26 · **근거**: [devlog/2026-09-26 12절](../devlog/2026-09-26_Step1-data_store.md)

| 처음 | 지금 |
|---|---|
| 없는 계좌는 LLM이 `uncertain`을 고를 것이라 기대 | LLM이 고른 이름이 사용자 말에 글자로 없으면 **"'여행 자금' 계좌로 이해했어요."** 를 먼저 밝힘 |

**왜**: "휴가비 계좌"(없는 이름)를 LLM이 여행 자금으로 **추측**했다. 대화 기록 탓인지 **통제 실험**(새 대화에서 단독 질문)으로 확인했더니 아니었다 — LLM의 뜻으로 추측하는 경향이었다. 프롬프트로 막으면 "여행 갈 때 쓰는 통장"까지 막힐 수 있어서, **막지 않고 알려주기**로 했다.

### B12. 문서 구성

**날짜**: 2026-09-26

| 처음 | 지금 |
|---|---|
| 기획서 하나에 기획과 설계가 함께 (설계 결정이 생길 때마다 기획서를 고침) | **기획서**(고정) / **설계서**(자라남) / **설계변경기록**(추가만) / 구현계획 / 개발일지 |

**왜**: 기획서를 계속 덮어써서 처음 계획이 무엇이었는지가 문서로 보이지 않게 됐다. 실무의 PRD · Design Doc · ADR 구분을 따랐다.

### B13. LLM에 대화 기록 대신 이전 상태를 넘긴다

**날짜**: 2026-09-28 · **근거**: [devlog/2026-09-28](../devlog/2026-09-28_Step4-CLI-이전상태.md)

| 처음 | 지금 |
|---|---|
| LLM에 대화 기록 최근 10개를 넘김. `intent`·`params`는 한 턴짜리로 `understand`가 매번 통째로 새로 씀 | LLM에 **지금 말 하나 + `<이전 상태>`**(직전 업무·값·이어받을 계좌·보여준 후보)만 넘김. `intent`·`params`는 **턴을 넘어 유지**하고, 바꿀지는 LLM이 이번 말의 뜻으로 판단 |

**왜**: Checkpointer가 직전 값을 이미 들고 있는데 버리고, 대신 대화 기록을 통째로 다시 읽히고 있었다. 토큰이 대화 길이만큼 늘고, 옛 대화가 해석을 끌고 갈 위험도 있었다(C2). 매 턴 새로 쓰면 "아니 5만 원"에서 계좌를 다시 물어야 한다. 합치기(유지·변경·추가·전체)는 말의 뜻이라 **코드 규칙이 아니라 LLM이** 한다 — "전부"를 계좌 이름이 없다고 이전 값으로 두면 LLM을 쓰는 의미가 없다. C2는 이것으로 해소.

### B14. 다른 업무로 넘어갈 때 이어받을 계좌 — 하나일 때만, 코드가 정한다

**날짜**: 2026-09-28 · **근거**: [devlog/2026-09-28](../devlog/2026-09-28_Step4-CLI-이전상태.md)

| 처음 | 지금 |
|---|---|
| (B13 논의 중 1차 결정) "거기서", "그 계좌"처럼 **가리키는 말이 있을 때만** 이어받음. 판단은 LLM | 직전에 본 계좌가 **하나**면 말하지 않아도 이어받음("생활비" 조회 후 "저축으로 3만 원" → 출금 = 생활비). 둘 이상이면 되묻기. **몇 개인지는 코드**(`_carry_account`)가 세서 `<이전 상태>`에 적음 |

**왜**: 계좌를 조회한 뒤 이체를 말하는 건 그 계좌에서 보내려는 흐름이다 (은행 앱의 계좌 상세 → [이체] 버튼과 같음). 이체는 어차피 승인을 거치므로 안전망이 있다. 처음엔 "하나뿐이면"을 LLM에 맡겼는데, **두 계좌를 "하나뿐"으로 잘못 세서** 테스트가 실패했다 → 세는 일은 사실이라 코드로 옮겼다. 이체 직후처럼 계좌가 둘(출금·입금)이면 어느 쪽인지 모르므로 되묻는다. 이어받은 계좌는 승인 화면에서 밝힌다 (Step 5).

### B15. 없는 종류의 계좌는 처리 불가가 아니라 후보 안내

**날짜**: 2026-09-28

| 처음 | 지금 |
|---|---|
| "주식 계좌 잔액"을 LLM이 `unsupported`로 고르기도 함 ("처리할 수 없는 요청") | 계좌 업무를 원했으면 **그 업무 + `uncertain`** → "이 중에서 골라 주세요: …" |

**왜**: 계좌에 접근하려는 요청은 업무 안에 있다. 결과가 없었을 뿐이므로 막지 않고 올바른 방향으로 유도해야 사용자 경험이 좋다.
