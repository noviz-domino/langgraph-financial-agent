## 계획의 원칙

### 원칙 1 — 매 단계 끝에 실제로 돌려볼 수 있어야 한다

"다 만들고 나서 실행해본다"가 아니라, **각 단계가 끝날 때마다 뭔가 동작해야 한다.**
이런 방식을 **walking skeleton**(걸어다니는 뼈대)이라 부른다.
처음부터 끝까지 얇게 한 줄을 뚫어놓고, 거기에 살을 붙여나가는 것.

> 반대 방식(모든 노드를 다 만든 뒤 실행)은 처음 실행하는 순간 에러가 10개 쏟아져서
> 어디서부터 고쳐야 할지 알 수 없게 된다.

### 원칙 2 — 의존성이 없는 것부터 만든다

`data_store.py`는 아무것도 의존하지 않고, 나머지 전부가 그것에 의존한다. 그래서 맨 먼저.

```
data_store.py  ←  functions.py  ←  graph.py  ←  main.py
   (의존 없음)                                   (전부 의존)
```

### 원칙 3 — 한 단계 = 한 커밋

되돌리고 싶은 단위로 커밋한다. 단계마다 커밋 메시지를 미리 적어뒀다.

## Step 1 — `data_store.py`

> **목표**: JSON을 안전하게 읽고 쓰는 통로를 만든다. 다른 모든 코드가 여기에 의존한다.

### 작업

| 함수 | 하는 일 |
|---|---|
| `ensure_working_copy()` | `bank_data.json`이 없으면 원본을 복사해 만든다 |
| `load()` | 작업용 복사본을 읽어 dict로 반환 |
| `save(data)` | dict를 파일에 쓴다. **임시 파일에 쓴 뒤 이름 교체**(atomic write) |
| `reset()` | 원본을 다시 복사해 초기 상태로 되돌린다 |

### 왜 atomic write인가

파일에 직접 쓰다가 프로그램이 죽으면 JSON이 **반만 쓰인 채로** 남아 다음 실행에 아예 못 읽는다.
임시 파일에 다 쓴 뒤 이름만 바꾸면, 이름 바꾸기는 운영체제가 원자적으로 보장하므로
"완전한 이전 파일" 아니면 "완전한 새 파일" 둘 중 하나만 존재한다.

### 완료 기준

- [ ] `uv run python src/data_store.py` 실행 시 키 7개 출력 (파일 맨 아래 `if __name__ == "__main__":` 확인 블록)
- [ ] 파일 경로를 `Path(__file__)` 기준으로 잡음 → 어느 폴더에서 실행해도 같은 파일을 찾음
- [ ] `bank_data.json`이 자동 생성되고, `initial_data.json`은 변경되지 않음
- [ ] `save()` 후 다시 `load()` 하면 바뀐 값이 읽힘
- [ ] `reset()` 하면 초기 상태로 돌아감
- [ ] `uv run python src/integrity.py data/bank_data.json` 이 7/7 통과

## Step 3 — 최소 그래프 (조회 경로만)

> **목표**: `START → understand → route_request → read_task → respond → END`
> 가장 짧은 길 하나를 끝까지 뚫는다. 승인 관련 노드는 아직 안 만든다.

### 작업

| 만들 것 | 내용 |
|---|---|
| `AgentState` | TypedDict. 1차에 필요한 필드만 (`messages`, `intent`, `params`, `result`) |
| `understand` | Gemini로 의도·파라미터 추출 (Structured Output) |
| `route_request` | 조건부 Edge. 지금은 조회/그 외 2갈래만 |
| `read_task` | `functions.py`의 조회 함수 호출 |
| `respond` | 결과를 문장으로 |
| `build_graph()` | 노드·Edge 등록 후 `InMemorySaver`와 함께 compile |

### 이 단계에서 확인할 것

- `understand`가 "내 계좌 보여줘"를 `intent="account_list_with_balance"`로 분류하는가
- "생활비 잔액 얼마야?"에서 `account="생활비"` slot을 뽑아내는가
- 조건부 Edge가 제대로 갈라지는가
- intent 선택지를 프롬프트에 **직접 쓰지 않고** `intents.py`에서 가져오는가

> **주의**: 이 단계에서 처음으로 **Gemini API를 실제로 호출**한다.
> `.env`에 `GOOGLE_API_KEY`를 넣어둬야 한다 (`.env.example` 참고).
> 모델은 `gemini-3.5-flash-lite`를 기본으로 쓴다.

### 완료 기준

- [ ] `graph.get_graph().draw_mermaid()` 출력이 **설계도의 조회 경로 부분**과 일치 (승인 노드는 아직 없음)
- [ ] "내 계좌 목록 보여줘" 입력 시 계좌 4개가 문장으로 출력됨
- [ ] "생활비 잔액 얼마야?" 입력 시 생활비 계좌 1개만 출력됨

> CLI는 Step 4에서 만드므로, 이 단계에서는 `graph.py` 맨 아래 확인 블록에서
> `graph.invoke(...)`를 직접 불러 확인한다.

## Step 5 — 즉시이체 + 승인 흐름 ★ 이 프로젝트의 핵심

> **목표**: `plan_change → confirm_change(interrupt) → apply_change` 를 완성한다.

### 작업

| 만들 것 | 내용 |
|---|---|
| `TransferInstantHandler` | `validate` / `describe` / `apply` 3개 메서드. intent `transfer_instant` |
| 거래 구조 결정 | 이체 거래에 **상대 계좌를 기록할지** 결정 (기획서 7장 "검사하지 못하는 것" 참고) |
| `HANDLERS` | intent → Handler 레지스트리 |
| `plan_change` | Handler의 `validate` 호출, 처리안 확정 |
| `route_validation` | 검증 통과 여부로 분기 |
| `confirm_change` | `interrupt`로 중단, 응답을 승인/거절로 분류 |
| `route_decision` | 승인/거절 분기 |
| `apply_change` | **재검증 후** 실행 + 저장 |

### `quick_classify` — 규칙 우선, LLM은 예외적으로

```python
APPROVE_WORDS = ["응", "네", "예", "승인", "진행", "ㅇㅇ", "오케이"]
REJECT_WORDS  = ["아니요", "취소", "거절", "그만", "됐어"]   # "아니" 단독은 넣지 않는다
```

> "아니, 5만 원만"이 "아니"에 걸려 거절로 오분류되는 것을 막기 위해
> `REJECT_WORDS`를 구체적인 표현으로 좁힌다. 수정 요청 처리는 Step 8에서.

### 완료 기준

- [ ] "생활비에서 저축으로 10만원 옮겨줘" → 승인 질문이 뜨고 **그래프가 멈춤**

## Step 7 — 카드 일시 잠금 ★ 설계 검증 단계

> **목표**: **`graph.py`를 한 줄도 고치지 않고** 새 업무를 추가할 수 있는지 확인한다.

### 작업

`intents.py`는 이미 준비되어 있으므로 `functions.py`에만 추가한다.

```python
class CardLockTemporaryHandler:
    intent = "card_lock_temporary"            # intents.py의 이름과 똑같아야 함
    def validate(self, params, data): ...     # 카드 status가 active인지 검사 (잔액은 안 봄)
    def describe(self, plan): ...             # "생활비 카드를 일시 잠금합니다" 같은 승인 문구
    def apply(self, plan, data): ...          # cards의 status만 locked로 변경

HANDLERS = {h.intent: h() for h in [TransferInstantHandler, CardLockTemporaryHandler]}   # 한 줄 추가
```

> 필요한 slot(`card`)은 Handler에 다시 적지 않는다. `intents.py`에만 있다.

### 이 단계가 성공의 판정 기준

- [ ] **`graph.py` 변경 없음** ← 이게 핵심. 변경이 필요했다면 설계를 다시 봐야 함
- [ ] "생활비 카드 잠가줘" → 승인 질문 → "응" → 카드 상태가 `locked`로 변경
- [ ] 이미 잠긴 카드를 또 잠그려 하면 안내 메시지

> 만약 `graph.py`를 고쳐야 했다면, **무엇을 고쳐야 했는지를 기록**한다.
> 그것이 Handler 인터페이스에서 빠진 부분이고, 최종 설계 자료의 중요한 재료가 된다.

```
Step 1 (data_store)

                                 ↓

                                 ↓
```

Step 4까지 끝나면 **조회는 완전히 동작하는 프로그램**이 된다.

## 위험 요소와 대비

| 위험 | 어떻게 대비하나 |
|---|---|
| `understand`가 의도를 잘못 분류 | Structured Output(Pydantic)으로 허용값을 제한. 허용값은 `intents.py`에서 만든다 |
| intent 이름이 파일마다 어긋남 | `intents.py` 한 곳에만 정의 (Single Source of Truth) |
| 이체 후 거래 기록 누락 | `integrity.py`로 이체 후 장부 검사 |
| 계좌 별명이 모호함 ("생활비"가 2개) | 소유자 필터링 후에도 여러 개면 사용자에게 선택받음 (Step 8) |
| LLM 호출 비용 | 승인/거절은 규칙으로 처리해 호출 0회. 기본 모델은 `gemini-3.5-flash-lite` |
| 저장 중 프로그램 종료 | atomic write (Step 1) |
| 승인 대기 중 잔액 변경 | `apply_change`에서 재검증 (Step 5) |
