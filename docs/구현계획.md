## 계획의 원칙

### 원칙 1 — 매 단계 끝에 실제로 돌려볼 수 있어야 한다

"다 만들고 나서 실행해본다"가 아니라, **각 단계가 끝날 때마다 뭔가 동작해야 한다.**
이런 방식을 **walking skeleton**(걸어다니는 뼈대)이라 부른다.
처음부터 끝까지 얇게 한 줄을 뚫어놓고, 거기에 살을 붙여나가는 것.

> 반대 방식(모든 노드를 다 만든 뒤 실행)은 처음 실행하는 순간 에러가 10개 쏟아져서
> 어디서부터 고쳐야 할지 알 수 없게 된다.

### 원칙 2 — 의존성이 없는 것부터 만든다

`data_store.py`는 아무것도 의존하지 않고, 나머지 전부가 그것에 의존한다. 그래서 맨 먼저.

```
data_store.py  ←  functions.py  ←  graph.py  ←  main.py
   (의존 없음)                                   (전부 의존)
```

### 원칙 3 — 한 단계 = 한 커밋

되돌리고 싶은 단위로 커밋한다. 단계마다 커밋 메시지를 미리 적어뒀다.

## Step 1 — `data_store.py` ✅ 완료

> **목표**: JSON을 안전하게 읽고 쓰는 통로를 만든다. 다른 모든 코드가 여기에 의존한다.

### 작업

| 함수 | 하는 일 |
|---|---|
| `ensure_working_copy()` | `bank_data.json`이 없으면 원본을 **`save()`로** 복사해 만든다 |
| `load()` | 작업용 복사본을 읽어 dict로 반환. 복사본이 없으면 먼저 만든다 |
| `save(data)` | **무결성 검사 후** 임시 파일에 쓰고 이름 교체(atomic write). 검사 실패 시 `IntegrityError` |
| `reset()` | 원본을 다시 복사해 초기 상태로 되돌린다 |

### 함께 정한 것 (근거는 [devlog/2026-09-26](../devlog/2026-09-26_Step1-data_store.md))

| # | 결정 |
|---|---|
| 1 | 저장 전 무결성 검사, 실패하면 파일에 안 씀. 에러 계층 `DataStoreError` > `IntegrityError` / `StorageError` |
| 2 | 복사본은 `load()`가 필요할 때 자동으로 만들고 로그를 남김 (lazy initialization) |
| 3 | atomic write — 같은 폴더의 고정 이름 `.tmp`, `fsync` 후 `os.replace`, 실패하면 `.tmp` 정리 |
| 4 | UTF-8, `ensure_ascii=False`, `indent=2`, 파일 끝 줄바꿈. 복사도 "원본 읽기 → `save()`" |

### 왜 atomic write인가

파일에 직접 쓰다가 프로그램이 죽으면 JSON이 **반만 쓰인 채로** 남아 다음 실행에 아예 못 읽는다.
임시 파일에 다 쓴 뒤 이름만 바꾸면, 이름 바꾸기는 운영체제가 원자적으로 보장하므로
"완전한 이전 파일" 아니면 "완전한 새 파일" 둘 중 하나만 존재한다.

### 완료 기준

- [x] `uv run python src/data_store.py` 실행 시 키 7개 출력 (파일 맨 아래 `if __name__ == "__main__":` 확인 블록)
- [x] 파일 경로를 `Path(__file__)` 기준으로 잡음 → 어느 폴더에서 실행해도 같은 파일을 찾음
- [x] `bank_data.json`이 자동 생성되고, `initial_data.json`은 변경되지 않음
- [x] `save()` 후 다시 `load()` 하면 바뀐 값이 읽힘
- [x] `reset()` 하면 초기 상태로 돌아감
- [x] `uv run python src/integrity.py data/bank_data.json` 이 7/7 통과
- [x] (추가) 무결성 위반 데이터는 `IntegrityError`로 거부되고, 파일은 저장 전 그대로

### 결정 사항 확인

- 소유자 필터링을 **여기서** 한다. user_02의 "생활비"가 결과에 섞이면 안 된다.
- `data_store.save`를 **import하지 않는다** (설계 원칙 2).
- 함수 이름은 intent 이름과 **똑같이** 한다 (`intents.py`의 `account_list_with_balance`).
- **글자를 다듬어 검색하지 않는다.** 이름은 `understand`에서 이미 "내 계좌 이름 목록" 중에서 골라져 온다 (설계서 6장 규칙 4). 이 함수는 **걸러내기만** 한다.
- 돌려줄 값: **`account_id`·`nickname`·`balance`** — ID는 사용자에게 안 보여주고 "그 계좌에서 보내줘" 같은 후속 대화용. 잔액은 숫자 그대로 (꾸미기는 `respond`)
- 내 계좌에 없는 이름이 들어오면 **`ValueError`** — 앞 단계가 약속을 어긴 버그이므로 조용히 빼지 않고 드러낸다

## Step 3 — 최소 그래프 (조회 경로만) ✅ 완료

> **목표**: `START → understand → route_request → read_task → respond → END`
> 가장 짧은 길 하나를 끝까지 뚫는다. 승인 관련 노드는 아직 안 만든다.

### 작업

| 만들 것 | 내용 |
|---|---|
| `AgentState` | TypedDict. 지금 쓰는 칸만: `messages`(대화 내내), `intent`·`params`·`inferred`·`result`(한 턴짜리) |
| `understand` | 허용 목록을 실행할 때 만들어(`create_model`) Gemini **1회** 호출 (Structured Output). LLM을 부르는 유일한 노드 |
| `route_request` | 조건부 Edge. 지금은 조회 / 그 외 2갈래만 |
| `read_task` | `READ_TASKS` 표에서 조회 함수를 찾아 실행 |
| `respond` | `READ_TASKS` 표에서 문장 틀을 찾아 문장 생성 (**LLM 미사용**) |
| `build_graph()` | 노드·Edge 등록 후 `InMemorySaver`와 함께 compile. `READ_TASKS`와 `READ_INTENTS`가 맞는지 먼저 확인 |

### 함께 정한 것 (근거는 [devlog/2026-09-26](../devlog/2026-09-26_Step1-data_store.md) 12절)

| # | 결정 |
|---|---|
| 1 | State 칸은 지금 쓰는 것만. `messages`는 `add_messages`, 판단 근거(`reason`)는 State가 아니라 **로그**로. 한 턴짜리 칸은 `understand`가 매번 새로 씀 |
| 2 | intent와 모든 slot을 한 번에 받고, 고른 intent의 slot만 남김. intent에 `unsupported` 추가. LLM 실패 시 "이해하지 못했어요" (재시도는 Step 6) |
| 3 | `respond`는 **정해진 틀**로. 틀은 `functions.py`에 업무 함수와 나란히 |
| 4 | LLM이 **뜻으로 추측한 이름**(사용자 말에 글자로 없음)은 **"'여행 자금' 계좌로 이해했어요."** 로 해석을 밝힘 — 막지 않고 알려주기 |

| 상황 | 지금 | 나중 |
|---|---|---|
| 이체·카드 잠금 요청 | "즉시이체 기능은 아직 준비 중이에요" | Step 5·7 |

| LLM 실패 | "요청을 이해하지 못했어요" | Step 6 자동 재시도 |

- `understand`가 "내 계좌 보여줘"를 `intent="account_list_with_balance"`로 분류하는가

## Step 5 — 즉시이체 + 승인 흐름 ★ 이 프로젝트의 핵심

> **목표**: `plan_change → confirm_change(interrupt) → apply_change` 를 완성한다.

### 작업

| 만들 것 | 내용 |
|---|---|
| `TransferInstantHandler` | `validate` / `describe` / `apply` 3개 메서드. intent `transfer_instant` |
| 업무 검사 (`validate`) | 금액 > 0, 출금 ≠ 입금, 잔액 충분 — 어기면 **사유를 담아 거절** (에러 아님, 설계서 6장 규칙 5) |
| 거래 구조 결정 | 이체 거래에 **상대 계좌를 기록할지** 결정 (설계서 5장 "검사하지 못하는 것", 설계변경기록 C1) |
| `HANDLERS` | intent → Handler 레지스트리 |
| `plan_change` | Handler의 `validate` 호출, 처리안 확정 |
| `route_validation` | 검증 통과 여부로 분기 |
| `confirm_change` | `interrupt`로 중단, 응답을 승인/거절로 분류 |
| `route_decision` | 승인/거절 분기 |
| `apply_change` | **재검증 후** 실행 + 저장 |

### `quick_classify` — 규칙 우선, LLM은 예외적으로

```python
APPROVE_WORDS = ["응", "네", "예", "승인", "진행", "ㅇㅇ", "오케이"]
REJECT_WORDS  = ["아니요", "취소", "거절", "그만", "됐어"]   # "아니" 단독은 넣지 않는다
```

> "아니, 5만 원만"이 "아니"에 걸려 거절로 오분류되는 것을 막기 위해
> `REJECT_WORDS`를 구체적인 표현으로 좁힌다. 수정 요청 처리는 Step 8에서.

### 완료 기준

- [ ] "생활비에서 저축으로 10만원 옮겨줘" → 승인 질문이 뜨고 **그래프가 멈춤**
- [ ] 이 시점에 `bank_data.json`이 **변경되지 않았음**을 확인
- [ ] "응" 입력 → 이체 실행, 잔액 변경 확인
- [ ] "취소" 입력 → 잔액 그대로
- [ ] 이체 후 `uv run python src/integrity.py data/bank_data.json` 이 7/7 통과 (거래 기록 누락 없음)

### 커밋

```
feat: 즉시이체와 승인 흐름 구현 (interrupt 기반 HITL)
```

## Step 6 — 실패·거절 경로

> **목표**: 잘 안 될 때의 흐름을 완성한다. 여기가 초보 설계와 실무 설계가 갈리는 지점.

### 작업

| 만들 것 | 내용 |
|---|---|
| `record_result` | `requests` 배열에 성공·실패·취소 기록 |
| `rollback` | 저장 실패 시 변경 전 상태 유지 보장 |
| `route_save` | 저장 성공 여부로 분기 |
| 검증 실패 안내 | 잔액 부족, 없는 계좌, 음수 금액 |

### 확인할 실패 케이스

| 입력 | 기대 동작 |
|---|---|
| "비상금에서 저축으로 50만원" | 잔액 부족(75,000원) 안내. 승인 질문 안 뜸 |
| "생활비에서 저축으로 -1만원" | 금액이 잘못됐다고 안내 |
| "없는계좌에서 저축으로 1만원" | 계좌를 못 찾았다고 안내 |
| 승인 질문에 "취소" | `requests`에 `cancelled`로 기록 |

### 완료 기준

- [ ] 위 4가지가 모두 의도대로 동작
- [ ] 실패·취소해도 `bank_data.json`의 잔액이 변하지 않음
- [ ] `requests` 배열에 기록이 쌓임

### 커밋

```
feat: 실패·거절 경로와 처리 기록 구현
```

## Step 7 — 카드 일시 잠금 ★ 설계 검증 단계

> **목표**: **`graph.py`를 한 줄도 고치지 않고** 새 업무를 추가할 수 있는지 확인한다.

### 작업

`intents.py`는 이미 준비되어 있으므로 `functions.py`에만 추가한다.

```python
class CardLockTemporaryHandler:
    intent = "card_lock_temporary"            # intents.py의 이름과 똑같아야 함
    def validate(self, params, data): ...     # 카드 status가 active인지 검사 (잔액은 안 봄)
    def describe(self, plan): ...             # "생활비 카드를 일시 잠금합니다" 같은 승인 문구
    def apply(self, plan, data): ...          # cards의 status만 locked로 변경

HANDLERS = {h.intent: h() for h in [TransferInstantHandler, CardLockTemporaryHandler]}   # 한 줄 추가
```

> 필요한 slot(`card`)은 Handler에 다시 적지 않는다. `intents.py`에만 있다.

### 이 단계가 성공의 판정 기준

- [ ] **`graph.py` 변경 없음** ← 이게 핵심. 변경이 필요했다면 설계를 다시 봐야 함
- [ ] "생활비 카드 잠가줘" → 승인 질문 → "응" → 카드 상태가 `locked`로 변경
- [ ] 이미 잠긴 카드를 또 잠그려 하면 안내 메시지

> 만약 `graph.py`를 고쳐야 했다면, **무엇을 고쳐야 했는지를 기록**한다.
> 그것이 Handler 인터페이스에서 빠진 부분이고, 최종 설계 자료의 중요한 재료가 된다.

### 커밋

```
feat: 카드 일시 잠금 구현 (그래프 수정 없이 Handler만 추가)
```

## Step 8 — 루프 2개

> **목표**: 되묻기(루프 1)와 승인 전 수정(루프 2)을 붙인다.

## 위험 요소와 대비

| 위험 | 어떻게 대비하나 |
|---|---|
| `understand`가 의도를 잘못 분류 | Structured Output(Pydantic)으로 허용값을 제한. 허용값은 `intents.py`에서 만든다 |
| intent 이름이 파일마다 어긋남 | `intents.py` 한 곳에만 정의 (Single Source of Truth) |
| 이체 후 거래 기록 누락 | `integrity.py`로 이체 후 장부 검사 |
| 계좌 별명이 모호함 ("생활비"가 2개) | 허용 목록을 내 계좌로만 만들어 user_02의 생활비는 후보에도 없음. 그래도 모르면 LLM이 `uncertain` → 되묻기 (Step 8) |
| LLM이 그럴듯하지만 틀린 계좌를 고름 | 조회는 결과로 드러남. 변경은 `confirm_change`가 실제 이름과 방향을 보여주며 확인 |
| LLM 호출 비용 | 승인/거절은 규칙으로 처리해 호출 0회. 기본 모델은 `gemini-3.5-flash-lite` |
| 저장 중 프로그램 종료 | atomic write (Step 1) |
| 승인 대기 중 잔액 변경 | `apply_change`에서 재검증 (Step 5) |
